# Local Delivery — Development with Claude

## Project Context

A last-mile delivery platform (DoorDash-shaped): customers order from local merchants, the system finds a nearby driver, and everyone watches the order move in real time. The hard problem is the **matching loop** — turning "an order was placed" into "a specific driver accepted it" while being fair to drivers, fast for customers, and resilient when the matching path itself degrades. The design leans on Redis geo-indexing for "who's nearby," a sequential-offer protocol for "who gets it," WebSockets for "where is it now," and a circuit breaker so a sick matcher fails into a retry queue instead of taking orders down.

**Learning goals:** real-time geospatial queries, a fair dispatch protocol, WebSocket + pub/sub fan-out, and protecting a critical-path algorithm with a circuit breaker.

## Architecture at a Glance (what actually runs)

Two datastores — this matches `docker-compose.yml` and `backend/package.json`:

| Store | Client | Role | Why this one |
|-------|--------|------|--------------|
| **PostgreSQL 16** (`pg`) | Source of truth | `users`, `drivers`, `merchants`, `menu_items`, `orders`, `order_items`, `driver_offers`, `ratings`, `delivery_zones`, `sessions`, `driver_location_history`, `idempotency_keys`, `retention_policies` | ACID for the order lifecycle and the durable audit of offers/ratings |
| **Redis / Valkey 7** (`ioredis`) | Real-time layer | Driver geo-index (`GEOADD`/`GEOSEARCH`), session cache, pub/sub for live updates | Sub-ms proximity queries on the matching critical path; PostGIS at ~5–10ms is too slow per match |

Backend is a single Express app (port 3000) with routes `auth`, `orders`, `driver`, `merchants`, `admin`, plus a native `ws` WebSocket server at `/ws` and three background jobs (dispatch sweeper every 5 s, geo-index prune every 30 s, hourly idempotency cleanup). The order logic lives under `services/order/`: `pricing` (zod validation, integer-cent pricing), `create`, `stateMachine` (guarded transitions), `cancel`, `assignment` (offers and the atomic claim), `dispatch` (leases and the sweeper), `matching`, `delivery`, `tracking`. Cross-cutting `shared/` modules: `circuitBreaker` (Opossum), `idempotency`, `errors`, `schemas`, `metrics` (prom-client), `retention` (data-cleanup jobs), `logger` (pino). `websocket/` holds the handler and a reference-counted `channelRegistry`. Frontend: React 19 + TanStack Router + Zustand, with customer, driver, and admin interfaces.

## Key Design Decisions

### 1. Redis geo-index for driver location, not PostGIS
Driver positions are written to a Redis geo set and matched with `GEOSEARCH`; PostgreSQL keeps only `driver_location_history` for after-the-fact analysis. Trade-off: "who's within N km of this merchant" sits on the order critical path and runs constantly as drivers move, so we want the sub-millisecond answer Redis gives rather than PostGIS's ~5–10ms per query. What we give up is durability of live positions — a Redis flush loses current locations (rebuilt on the drivers' next ping) — which is acceptable because live location is inherently ephemeral while the trip record in Postgres is not.

### 2. Sequential driver offers, not broadcast
`startDriverMatching` finds the best available driver, creates a **time-limited `driver_offers` row (30s)**, and polls for accept/reject/expire before moving to the next-best driver, excluding those already offered (read from `driver_offers`), up to `MAX_OFFER_ATTEMPTS`. Trade-off: broadcasting to all nearby drivers would fill the order faster but creates a race (two drivers "win" the same order) and is unfair (fastest tapper wins every time). Sequential offers give each driver an exclusive window — at the cost of higher time-to-assign, bounded by the 5-offer cap and a 5-minute dispatch deadline. Sequencing alone does not make acceptance safe; that comes from the claim transaction and the partial unique indexes (see the 2026-10-10 log entry).

### 3. Driver scoring is multi-factor, not nearest-only
`calculateDriverScore` weights **distance 40%, rating 25%, acceptance rate 20%, current load 15%** (normalized against a 5km max). Trade-off: pure nearest-driver minimizes ETA but ignores reliability — a close driver who routinely rejects or is already juggling deliveries is a worse pick than a slightly-farther dependable one. The weights bias toward proximity while still pricing in reliability; the cost is a heuristic that needs tuning against real acceptance data.

### 4. Circuit breaker around matching with a lease-based retry
The matcher is wrapped in an Opossum breaker (opens at 50% errors over 3+ calls, resets after 30 s). When open, or when a run throws or times out, the **fallback releases the order's dispatch lease with a 30-second back-off**; the dispatch sweeper (on any instance) retries it afterwards. Trade-off: while open, orders wait instead of matching immediately — but the alternative (every order blocking on a degraded matcher, e.g. Redis latency spiking) cascades into a total outage. Failing fast keeps the rest of the API — browsing merchants, tracking in-flight orders — alive.

### 5. Native WebSocket + Redis pub/sub for live tracking
Order status and driver-location updates push over a native `ws` server; Redis pub/sub distributes messages so any API instance can deliver to a connected client. Each process holds one Redis subscriber shared by all its sockets, every subscription starts with an `order_snapshot`, and status events carry the order's `version`. Trade-off vs. Socket.io: fewer features (no built-in rooms/reconnection) but lower overhead and no dependency, which suits point-to-point order tracking. Trade-off vs. polling: persistent connections cost server memory, justified by the second-by-second freshness a live map needs.

## Current State

Implemented and running end to end: session auth (bcrypt + Redis-cached sessions in Postgres), merchant/menu browsing, server-priced quotes, idempotent order placement (key, order and items in one transaction), the sequential-offer matching loop with multi-factor scoring, dispatch leases with a `SKIP LOCKED` sweeper and the Opossum breaker, the atomic accept (offer, order and courier in one transaction, backed by partial unique indexes), a guarded order state machine with a `version` column, a liveness-filtered Redis geo index (`GEOSEARCH` + last-seen sorted set + prune), sampled location persistence, stage-aware ETAs, WebSocket tracking with snapshots and versioned events, ratings, Prometheus metrics, `pino` logging, graceful shutdown, and data-retention cleanup jobs. Frontend has customer ordering (server quote, one idempotency key per checkout attempt), live order tracking that resyncs after reconnects, a driver dashboard with offer accept/reject, heartbeat pings and missed-offer recovery, and an admin dashboard. Backend tests: `npm test` (vitest, 61 tests, offline). Seeded accounts (customers, drivers, admin) all log in with **`password123`**.

Intentionally omitted: map visualization of the live driver (tracking data flows over WebSocket but there's no map widget), multi-stop/batched routing (TSP), surge pricing, demand prediction, PostGIS, a merchant API, and rate limiting.

## Iteration & Repair Log

- **2026-10-10 — exactly-once dispatch, guarded transitions, live-tracking contract, docs rewrite.** A runtime probe of the old code confirmed: a customer could cancel an order while its offer was open and the driver's Accept then resurrected it to `driver_assigned` (unguarded `UPDATE`, driver left busy); the matcher returned "expired" for an accept that landed between its last poll and the deadline, so the order could go to a second driver; a reused `X-Idempotency-Key` from another customer returned the first customer's order (address included); a quantity of -3 or an item from another merchant's menu was priced into the order (total -$28.49); the tip route always failed with 500 (it passed the status as the order id and concatenated DECIMAL strings); `driver_location_history` was never written (the sampler compared against the timestamp it had just written) while every ping wrote PostgreSQL; drivers who stopped pinging stayed matchable forever; matching lived only in process memory and the breaker's "retry queue" was a no-op; and `init.sql` could not be loaded twice. Fixes: `services/order/stateMachine.ts` (transition table, compare-and-set `UPDATE`s that bump a new `orders.version`, 404/403/409 from the current row); a transactional claim in `assignment.ts` plus three partial unique indexes on `driver_offers` (one pending per order, one pending per driver, one accepted per order) and a compare-and-set offer expiry; `cancel.ts` withdraws the live offer in the cancel's transaction; `dispatch.ts` adds `dispatch_owner`/`dispatch_lease_until`, a `FOR UPDATE SKIP LOCKED` sweeper and lease release on shutdown, and the matcher reads exclusions from `driver_offers`; `shared/idempotency.ts` now runs key + order + items in one transaction, scoped per user with a SHA-256 request fingerprint (422 on reuse, 409 after a 5 s lock wait); `pricing.ts` validates with zod and prices in integer cents, shared by the new `POST /orders/quote`; the geo layer uses `GEOSEARCH` + a `drivers:last_seen` sorted set (30 s, `LOCATION_STALE_MS`) and a Lua prune; durable location writes go through a `SET NX PX 10000` gate; the WebSocket handler uses one Redis subscriber per process (`channelRegistry.ts`), sends `order_snapshot` on subscribe, moves trackers to the courier's channel on assignment, computes stage-aware ETAs and runs a ping/pong heartbeat. ## Open Questions

1. **Driver goes offline mid-delivery:** still unhandled. Going offline is refused while a delivery is active, but a phone that simply dies leaves the order `driver_assigned`. A liveness lease on active deliveries (no ping for N minutes → back to dispatch) needs a transition out of `driver_assigned` that also releases the driver — how long before reassigning?
2. **Offer latency vs. fill rate:** 30s sequential offers can be slow to fill in low-density areas. Is a hybrid (broadcast to top-K with first-accept-wins) worth it now that the claim transaction would make it safe, given the herd it creates?
3. **When to dispatch:** with no merchant API, matching starts at `pending` and prep time only feeds the ETA. Dispatching at confirmation + prep − travel would get couriers to the counter as the food is ready; it needs the merchant flow first.
4. **Seed-vs-init split:** both files are now re-runnable, but `docker-compose up` still loads only the schema. Mount the seed too, or add a `db:seed` script?
5. **Batching:** multi-order pickup from one merchant (TSP over drop-offs) would raise driver efficiency — where does the added routing complexity pay off?
