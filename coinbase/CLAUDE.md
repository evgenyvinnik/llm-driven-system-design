# Coinbase (Crypto Exchange) — Development with Claude

## Project Context

An exchange is the one system in this repo where **the database is not fast enough to be the source of truth on the hot path**. Order matching is a tight loop over a sorted structure — find the best bid, find the best ask, check whether they cross, execute, repeat — and doing that with SQL round trips per comparison means the matching latency is dominated by network hops rather than by matching. Real exchanges keep the book in memory and treat the database as a durable log of what already happened. This project does the same, which immediately creates the central tension: the authoritative book lives in a process that can die.

The second problem is that **money cannot be a float**, and the naive fix isn't enough. Every monetary column is `DECIMAL(28,18)` and every API response returns amounts as strings, because a JSON number is an IEEE-754 double and `0.1 + 0.2 !== 0.3` is a rounding error you cannot explain to someone who just lost satoshis. Serializing as strings pushes the burden onto the frontend to format rather than compute — which is the correct place for it, since the frontend never needs to do arithmetic.

The third is double-spend prevention while orders are resting. A user with 1 BTC must not be able to place two 1-BTC sell orders. There's no lock to take because the "resource" is a balance, not a row you're mutating. The answer is the reserve pattern: `available = balance - reserved_balance`, with reservation happening as a single conditional `UPDATE` whose `WHERE` clause *is* the check.

**Learning goals:** in-memory order books with price-time priority, decimal precision discipline end to end, balance reservation as compare-and-set, WebSocket channel fan-out, and simulating a live market with Geometric Brownian Motion.

The matching engine is `services/orderBook.ts` (per-symbol `OrderBook` with `bids` sorted price-DESC/sequence-ASC and `asks` price-ASC/sequence-ASC, BigInt amounts from `services/decimal.ts`, managed by `orderBookManager`). `services/orderService.ts` orchestrates validation → (pair queue) hold + insert → match → per-trade settlement → hold release, plus cancellation, stop triggers and boot rehydration. `services/pairQueue.ts` serializes commands per pair, `services/stopOrders.ts` holds untriggered stops, `services/exchangeAccount.ts` provides liquidity of last resort and collects fees, `services/walletService.ts` has the ledger primitives, and `services/marketService.ts` is the GBM simulator. Support modules: `idempotency.ts`, `rateLimiter.ts` (separate `apiLimiter`, `authLimiter`, `orderLimiter`), `metrics.ts`, `logger.ts`, `db.ts`, `kafka.ts`. Frontend is React + TanStack Router + Zustand + Tailwind on 5173 with TradingView `lightweight-charts`, a depth-bar order book, and `hooks/useWebSocket.ts` driving live ticks. `backend/src/app.test.ts` is a vitest suite over the HTTP surface with shared modules mocked.

## Key Design Decisions

### 1. The order book is in memory; Postgres is the durable record of what already executed
`orderBookManager.getBook(symbol)` returns a per-symbol `OrderBook` holding two arrays with sorted insertion, and `match(incoming)` walks the opposite side until it stops crossing the incoming order's limit. A database-backed book — `SELECT … ORDER BY price DESC LIMIT 1` per iteration — turns each matching step into a network round trip plus query planning, so a single order crossing ten levels costs ten round trips and matching latency becomes entirely I/O. Worse, it makes correctness harder rather than easier: you'd need `SERIALIZABLE` or explicit locking to stop two concurrent matchers from consuming the same resting order, which serializes exactly the operation you most want fast. Keeping the book in memory makes matching a single-threaded pass over sorted arrays with no concurrency to reason about at all. What we give up is that the authoritative book lives in a process that can die, so it has to be rebuilt. At boot, before `server.listen`, `rehydrateOrderBooks()` replays every live order from Postgres in `arrival_seq` order. `arrival_seq` is a `BIGSERIAL` assigned at insert and is also the in-memory tie-breaker, so the replayed book has exactly the priority the lost one had. If a settlement transaction fails mid-match, the pair's book is rebuilt the same way, because memory has already consumed resting quantity the database never recorded. What remains given up is multi-instance operation: each process owns an unrelated book (decision 7).

### 2. Balance reservation is a single conditional UPDATE, not read-then-write
`reserveBalance()` is one statement: `UPDATE wallets SET reserved_balance = reserved_balance + $3 WHERE user_id = $1 AND currency_id = $2 AND (balance - reserved_balance) >= $3 RETURNING id`, and the caller treats a zero row count as "insufficient funds." The obvious implementation — `SELECT` the balance, compare in application code, then `UPDATE` — has a race the size of the round trip between the two statements: two orders placed concurrently both read the same available balance, both pass the check, and both reserve, taking `reserved_balance` above `balance`. Folding the predicate into the `WHERE` clause makes the check and the mutation the same atomic operation, so the loser simply updates zero rows. The schema backs it with `CHECK (balance >= reserved_balance)` so even a bug elsewhere cannot persist an over-reserved wallet. The cost is that failure is signalled by a row count rather than an exception, which is easy to ignore — every caller has to remember that a successful query can still mean rejection.

### 3. Every monetary value crosses the API boundary as a string
`DECIMAL(28,18)` in Postgres, strings in JSON, formatting (never arithmetic) in `frontend/src/utils/format.ts`. Returning JSON numbers is the default thing to do and it silently destroys precision: `JSON.parse` produces a double, 18 decimal places of a large balance do not fit in 53 bits of mantissa, and the corruption is invisible — no error, just a value that's slightly wrong and gets slightly wronger every round trip. Strings preserve the exact decimal representation the database produced. The trade-off is ergonomic friction: the frontend cannot sort or sum without an explicit parse, and every developer touching a balance has to think about it. That friction is the feature — it makes precision loss a deliberate act rather than an accident. The discipline now extends through the matching engine. `services/decimal.ts` holds amounts as BigInts scaled by 10^18, the same scale as the columns, so storage, transport and matching are all exact and conversion happens only at the boundaries. Parsing is strict: a regex instead of `parseFloat`, which used to accept `"12abc"` as 12, plus the pair's tick and step precision. The cost is that every arithmetic step is a named function call (`mul`, `mulCeil`, `roundToDecimals`) instead of an operator, and BigInt allocation in the hot loop. For an exchange where a rounding error is someone's money, that cost is the right one to pay.

### 4. Prices are simulated with Geometric Brownian Motion, not a random walk
`simulatePriceTick()` applies `S × exp((μ − σ²/2)·dt + σ·√dt·Z)` with per-asset volatility (BTC ~1.5%, DOGE ~5%), a small upward drift, a Box–Muller normal, and clamping to 50–200% of base price. A uniform random walk would be simpler and would produce prices that look wrong in ways that matter for testing: it can go negative, its volatility doesn't scale with price level, and its increments are additive so a $100 move means the same thing at $100 as at $100,000. GBM is multiplicative, so returns rather than absolute moves are normally distributed — which is why the candles look like real candles and why per-asset σ produces visibly different chart character. What we give up is real market microstructure. Each executed trade sets the price (`updatePriceFromTrade`) and the simulation continues from there, but resting depth exerts no pressure. A large order moves the price only as far as its last fill, and the walk then ignores the book again.

### 5. When the book runs out, the exchange account is the counterparty, inside a protection band
Market orders (and triggered stops) are immediate-or-cancel. They sweep the book down to a protection price 5% beyond the reference price; the remainder fills against the **exchange account** (`services/exchangeAccount.ts`) at the simulated market price, as a real trade against a real counter-order, and anything still left is cancelled with its hold released. Rejecting on an empty book would be more honest but makes a freshly seeded app untestable, since nobody has resting orders. The old answer was worse than either: `simulateMarketFill` credited the buyer with no counterparty and no trade row. That created value from nothing, and it left the market order in the book where it could match again. A counterparty account keeps every fill two-sided, so "trading conserves every currency" becomes a checkable invariant. The account also collects maker and taker fees. Its balances are minted at boot, and each top-up is recorded as a `deposit`, so the one place value enters the system is visible. The lesson the demo still gets slightly wrong is depth: there is always liquidity within 5%, which real thin markets don't have.

### 6. Holds are attributed per order and sized for the worst case
Each order carries `hold_remaining`: what it still has reserved. A buy reserves `quantity × worst price × (1 + taker fee)`, where the worst price is the limit price or, for market and stop orders, the protection price, because fills only happen at that price or better and the taker rate is the higher fee. Fills spend from the hold, and finishing or cancelling releases exactly what is left. The previous design kept only an aggregate `reserved_balance` and recomputed releases from the order's price. That leaked in both directions: price improvement left residue reserved forever, a market buy reserved at the current price could fill above it, and orders with a null price (market, stop) released nothing on cancel. Per-order attribution turns "reserved equals the sum of live holds" into an invariant you can query, and the `hold_remaining >= 0` CHECK turns overspending into a failed transaction. The cost is a column write per fill and over-reservation while an order is live, since a limit buy that will probably pay the maker fee still holds the taker fee.

### 7. Commands for one pair run one at a time (per process)
`services/pairQueue.ts` chains every command that touches a pair's book: place, cancel, stop trigger and rebuild. Matching itself is synchronous, but placement awaits Postgres several times. Without the queue, a cancel or a second order could run between "the book consumed this resting order" and "the fill committed", and the book and database would disagree. A database lock per pair would serialize the same work with a round trip per acquisition; the in-process promise chain is free and keeps different pairs concurrent. The honest limit is that it is a per-process lock pretending to be a sequencer. Two API instances would each own an unrelated book for every pair. The production fix is one owner per pair, like a partitioned command log, not a bigger lock.

## Current State

Runs end to end: `docker-compose up -d` (Postgres, Valkey, Zookeeper, Kafka; Kafka is optional, since publish failures are non-fatal), `npm run db:migrate` (idempotent, safe to re-run), backend on 3001, frontend on 5173, and optionally the two workers.

Implemented:
- **Accounts:** registration/login with bcrypt and Redis-backed sessions; per-currency wallets with per-order holds.
- **Orders:** market, limit and stop orders with per-user idempotency keys, Redis replay plus a `UNIQUE (user_id, idempotency_key)` backstop. Stop orders are armed and triggered by price ticks and trades.
- **Matching:** exact BigInt price-time-priority matching with partial fills, maker/taker roles and maker-price execution.
- **Settlement:** one transaction per trade covering trade row, both fills, wallets, quote-currency fees credited to the exchange account, and release of unspent holds.
- **Market orders:** immediate-or-cancel within a 5% protection band, with exchange-account liquidity of last resort.
- **Reliability:** cancellation in the pair queue with exact hold release; book rebuild at boot and after settlement failure.
- **History and portfolio:** trade and transaction history, 1-minute candle aggregation, portfolio snapshots and allocation breakdown.
- **Live updates:** WebSocket ticker and price broadcasts, plus a session-authenticated private `user:<id>` channel pushing `order_update`.
- **Operations:** per-process rate limiting split across API/auth/order tiers, Prometheus metrics.
- **Tests:** vitest suites over the HTTP routes (`app.test.ts`) and the matching engine (`services/matching.test.ts`).

**Seeded logins:** `alice` / `alice@example.com` and `bob` / `bob@example.com`, both `password123`. Alice starts with 100,000 USD.

Not built:
- real market data (GBM only);
- blockchain integration (deposits and withdrawals are `transactions` rows, not on-chain transfers);
- KYC;
- tiered fee schedules;
- stop-limit orders (stops are stop-market);
- self-trade prevention;
- multi-instance matching (decision 7).

## Iteration & Repair Log

- **2026-07 (docs rewrite):** replaced the phase-checklist CLAUDE.md with this structure. Its five phases were all marked **"(Complete)"**, including "Phase 4: Real-time Streaming — Price broadcaster worker (every 2 seconds)" — which is technically true and deeply misleading, because it hides that the worker's prices and the API's prices are two different simulations (below). The old file also had no entry for the WebSocket authentication gap or the split price universe, since a checklist has nowhere to put "this works but is wrong."
- **Two divergent price universes (design bug):** `index.ts` runs its own `setInterval` calling `marketService.simulatePriceTick()` and broadcasting over WebSocket, while `workers/price-broadcaster.ts` is a **separate process** with its **own in-process** `marketService` instance ticking independently and writing `price_candles` plus Kafka. Because `marketService` holds prices in a plain in-memory `Map` with no Redis backing, the prices users see and the candles persisted to the database drift apart from the first tick. Running `dev:server1/2/3` multiplies this — three instances, three unrelated markets, three unrelated order books.
- **WebSocket `authenticate` verifies nothing (fixed 2026-10-31, below):** `websocket.ts` handles `{type: 'authenticate', userId}` by trusting the client-supplied `userId` and subscribing that socket to `user:{userId}`. Any connected client can subscribe to any user's private channel by guessing or reading a UUID. The session cookie is available on the upgrade request and is not consulted.
- **`services/circuitBreaker.ts` is dead code:** the module exists and `opossum` is a declared dependency, but nothing imports it — `grep -r circuitBreaker src` matches only the file itself. Kafka publish failures are instead swallowed by a bare `catch (_err) {}` in the broadcaster.
- **Backend port pinned to 3001:** `dev` is `PORT=3001 NODE_ENV=development tsx watch src/index.ts`, matching both Vite proxy targets (`/api` → `http://localhost:3001`, `/ws` → `ws://localhost:3001`). `dev:server2`/`dev:server3` used to set `PORT` and then invoke `npm run dev`, which re-set `PORT=3001`, so they never bound 3002/3003. Fixed 2026-10-31: each runs `tsx watch` with its own `PORT`. Several instances still mean several unrelated books (decision 7).
- **2026-10-31 (order lifecycle rebuilt):** the order path had accounting bugs the docs only partly listed:
  - **Fee units:** `executeTradeTransfer` subtracted the buyer's fee, which is in quote currency, from the base amount they received. At BTC ≈ $65,000 a buy of 0.01 BTC was credited 0.01 − 1.3 = −1.29 BTC; the transaction then failed on `balance >= 0` *after* the trade row and both order fills had already committed in separate queries. Maker and taker fees were also assigned by side, not by who rested first.
  - **Holds:** price improvement left reserve stranded, and market and stop orders released nothing on cancel.
  - **Fake fills:** `simulateMarketFill` minted value with no counterparty and left the market order resting in the book.
  - **Unvalidated input:** `parseFloat` accepted junk quantities.
  - **Concurrency and recovery:** nothing serialized commands per pair, and nothing rebuilt the book.
  - **Broken `takerSide`:** the trades endpoint reported `bo.side` from the buy order, so it was always `buy`.

  Replaced with decisions 3, 5, 6 and 7 plus boot rehydration (decision 1). Verified against the live stack with a script that trades between alice and bob through limit, crossing, market, idempotent, cancelled and stop orders, then a restart. After each phase it checks three invariants: each currency's total across all wallets is unchanged, each wallet's `reserved_balance` equals the sum of its live orders' `hold_remaining`, and finished orders hold nothing. All 34 checks pass, plus 6 after the restart. One check was flaky and became a design note: a stop placed 50 cents below the price failed to fire within 40 s in one run in four. That is ordinary random-walk behaviour, so the check now drives the price through the stop with a real trade, which also exercises the "trade moves the price, so re-check stops" path.
- **2026-10-31 (WebSocket identity):** the `auth` message no longer trusts a client-supplied `userId`. The upgrade request runs through the same `express-session` middleware as the REST API, the server subscribes the socket to `user:<id>`, and `subscribe` refuses `user:` channels by name. That closes the hole where any socket could read any user's private channel by UUID, and makes the channel worth having: order state changes are now pushed there. This answers the old open question 4 in favour of reading the cookie at upgrade. The coupling to the session store is real, but it is the same store the REST API already trusts, and a signed ticket would add an issuance endpoint for no extra guarantee in a single-origin app.
- **2026-10-31 (frontend):** `npm run build` had been failing on a missing `vite-env.d.ts` and a `lightweight-charts` v5 `Time` type mismatch. Both are fixed. `useWebSocket`'s "connected" ref had skipped handler registration under StrictMode's double effect, and the chart was destroyed and recreated (losing the viewport) on every candle refresh; both are fixed. The trade form gained stop orders and a "funds held" line that explains the worst-case buy hold.

## Open Questions

1. Decision 7's queue is per process. What is the smallest correct multi-instance design: a Redis lease per pair with a fencing token checked on every settlement write, or route all commands for a pair to one owner through a partitioned log? Answering that also settles who is allowed to tick a pair's price, which reopens the old split-universe problem (the price worker and the API still run independent GBM simulations).
2. Any trade sets the market price (`updatePriceFromTrade`), and stops trigger off that price. With no self-trade prevention, one account can trade with itself at an extreme price and fire everyone's stops. Should stops trigger off a mark price (an index or a time-weighted price) instead of last trade, and should self-trades be cancelled at match time?
3. The exchange account mints its liquidity at boot. That keeps trading conservation-checkable, but the system's total supply now grows with every restart. Would a bounded market-maker bot quoting real resting orders around the simulated price be worth the extra moving part, since it would also make the order book visibly deep?
4. A buy holds the taker fee even when it will almost certainly rest and pay the maker fee. Is that over-reservation a problem worth solving with a re-hold step when an order rests, or is a conservative hold exactly what a ledger should do?
