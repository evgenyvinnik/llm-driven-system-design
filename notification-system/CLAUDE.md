# Notification System — Development with Claude

## Project Context

A notification system is mostly a routing and fan-out problem wearing a delivery costume. The hard parts aren't "call the push provider" — they're deciding *whether* to send at all (preferences, dedup, rate limits), *when* (priority), and *what happens when the provider fails* (retries, dead-lettering) — all while a burst of a million campaign notifications must not delay the one password-reset email someone is staring at.

That last constraint is what shapes the whole design: priority can't be a field you sort by, because a single queue with a million low-priority messages in front means the critical one waits regardless of its priority value. It has to be a separate queue with its own consumers.

**Learning goals:** priority-based queue processing, multi-channel routing, at-least-once delivery with retries and dead-letter handling, and honoring user preferences without putting a database read on the hot path.

## Architecture at a Glance (what actually runs)

| Component | Role |
|-----------|------|
| **API server** (`src/index.ts`, port **3001**) | Validates, applies preferences/quiet hours/dedup/rate limits, and commits the notification + per-channel delivery rows + outbox rows in one transaction. Needs only PostgreSQL and Redis |
| **Worker** (`src/workers/index.ts`) | Outbox relay (publishes due rows with publisher confirms, critical first), consumers for the 12 work queues and the dead-letter queue, and a lease sweeper |
| **RabbitMQ** | **13 queues**: `{push,email,sms} × {critical,high,normal,low}` plus one shared `notifications.dead_letter` (arguments unchanged since 2026-07) |
| **PostgreSQL** | `notifications`, `delivery_status` (per-channel state machine with lease + fencing), `delivery_outbox`, `notification_events`, `notification_preferences`, `device_tokens`, `notification_templates`, `campaigns`, `campaign_stats`, `users`, `sessions` |
| **Redis** | Preference cache (5-min TTL, deleted on write), idempotency records, content-dedup claims, rate-limit counters, session cache |

Services in `src/services/`: `notifications.ts` (accept path), `outbox.ts` (outbox writes + relay), `delivery.ts` (dedup claims, delivery claim/complete/retry/cancel, aggregate status), `preferences.ts` + `quietHours.ts` (time-zone-aware quiet hours), `rateLimiter.ts` (all-or-nothing Lua admission), `templates.ts`. The worker's per-message logic is `src/workers/deliveryHandler.ts`. Cross-cutting utilities in `src/utils/`: `rabbitmq.ts` (confirm channel, consumer re-registration, reconnect), `idempotency.ts`, `redis.ts`, `database.ts` (`withTransaction`), `circuitBreaker.ts` (breakers for push/email/sms), `retry.ts`, `metrics.ts`, `logger.ts`. Frontend is a React dashboard ("NotifyHub") over notifications, preferences, templates, campaigns, and an admin view.

Push/email/SMS providers are **simulated** with randomized success rates — which is the point: it exercises the retry and dead-letter paths on every run, something real providers would only do occasionally.

## Key Design Decisions

### 1. A queue per channel *and* per priority (13 queues), not one queue with a priority field
Priority as a sort key inside one queue doesn't survive contact with a campaign: a million queued marketing pushes sit ahead of the password-reset email, and no amount of "priority: critical" moves it forward — the consumer still has to work through what's already in flight. Separate queues let critical consumers stay idle and instantly available, and let us scale workers per channel independently (SMS is rate-limited and expensive; push is cheap and high-volume — they should never share a worker pool). What we give up is a combinatorial queue count: 3 channels × 4 priorities is already 13 queues to declare, monitor, and alarm on, and adding a channel adds four more. At a larger channel count this stops being manageable and would push toward RabbitMQ priority queues or a partitioned log.

### 2. At-least-once, with idempotency pushed to the consumer
Delivery is at-least-once. Exactly-once across an external provider isn't achievable — the provider can succeed and the ack can still be lost, and there's no distributed transaction spanning "RabbitMQ ack" and "APNs accepted". So the consumer makes repeats harmless: it claims the `(notification_id, channel)` row (`pending|retrying → sending`, `attempts + 1`, 60 s lease) before calling the provider, and a redelivered or duplicated message finds nothing to claim. `attempts` is the fencing token for the final write. Retries are outbox rows due later (budget of 5 attempts), and only an exhausted delivery is dead-lettered. The remaining duplicate window is a worker dying after the provider accepted — accepted, because a missing password reset is worse than a rare duplicate push.

### 3. Preferences cached in Redis with a 5-minute TTL
Every notification needs a preference check, so an uncached design puts a Postgres read in front of every single send — the database becomes the throughput ceiling for a system whose whole job is volume. The 5-minute TTL means a user who disables notifications can still receive one for up to five minutes. That's the explicit trade: bounded, short-lived staleness in exchange for taking the database off the hot path. Preference writes delete the cache key, so in practice a change applies to the next send and the TTL is only a backstop. What is still missing is a re-check at *send* time: a notification deferred by quiet hours is sent even if the user turns the channel off in the meantime.

### 4. The dead-letter queue must be declared *without* its own dead-letter exchange
This was a real bug, not a hypothetical. The queue list was iterated uniformly and every queue — including `notifications.dead_letter` — was declared with `x-dead-letter-exchange` arguments pointing at the dead-letter queue. RabbitMQ then saw the same queue declared with two different argument sets and returned **406 PRECONDITION_FAILED**, which killed the channel and, because nothing handled the error event, took down the whole API process. The fix is ordering plus an exclusion: declare `DEAD_LETTER` first with no DLX arguments, then declare the 12 work queues dead-lettering into it, skipping `DEAD_LETTER` in the loop. A dead-letter queue that dead-letters into itself is a cycle; it has to be the terminus.

### 5. The API does not talk to RabbitMQ at all
Originally the API published to RabbitMQ after inserting the notification, so `app.listen()` had to precede a background `initRabbitMQ()` to stay reachable while the broker started — and any broker failure between the insert and the publish left a notification that would never be sent. Since 2026-10 the API writes outbox rows in the same transaction as the notification, and the worker's relay publishes them. The API's availability no longer depends on the broker; a broker outage shows up as outbox lag (`/health` reports it), not as failed requests or lost notifications.

## Current State

Runs end to end: API on 3001 (Vite proxies `/api` → 3001) needing only PostgreSQL and Redis; the worker (`npm run dev:worker`) runs the outbox relay, the 12 work-queue consumers, the dead-letter consumer and the lease sweeper — without it, notifications are accepted but never delivered. Implemented: transactional outbox with priority-ordered relay and publisher confirms; scheduled and quiet-hours deliveries (quiet hours evaluated in the user's IANA time zone); idempotent leased/fenced delivery claims; durable retries with backoff and a 5-attempt budget; dead-lettering of exhausted and malformed messages; cancel that stops unstarted deliveries; `Idempotency-Key` on `POST /notifications` (caller-scoped, fingerprinted, `409`/`422`); atomic content dedup; all-or-nothing Redis rate limits; per-channel circuit breakers; Prometheus metrics; structured logging; liveness/readiness probes; and the NotifyHub dashboard. Seed users: `admin@example.com` (admin), plus `john@`, `jane@`, `bob@example.com`.

**Auth is demo-grade on purpose:** `POST /api/v1/auth/login` looks the user up by email and accepts any password, then issues a UUID session token stored in Postgres and cached in Redis. This project is about delivery mechanics, not authentication.

**Tests:** `cd backend && npm test` runs 25 offline vitest tests (quiet hours, aggregate status, idempotency, relay, delivery handler).

Not implemented: provider delivery receipts (webhooks), in-app notifications over a live stream, digests, provider failover, preference re-check at send time, category enforcement, and campaign fan-out as a background job (it runs inside the HTTP request).

  - *Dual write.* The API inserted the notification and then published to RabbitMQ; a broker error left a `pending` row forever, and the `delivery_status` 'pending' upsert ran *after* the publish, so a fast worker's `sent` could be overwritten back to `pending`. Now notification + delivery rows + `delivery_outbox` rows commit in one transaction and the worker's relay publishes them (`FOR UPDATE SKIP LOCKED`, ordered by priority, confirm channel with a 5 s timeout). The API no longer initializes RabbitMQ; `/health` reports outbox lag instead.
  - *Scheduled and quiet-hours notifications were never sent* — nothing ever read `status = 'scheduled'`. They are now outbox rows with a later `available_at`. Quiet hours used the server's clock; they are evaluated in the user's IANA zone with a DST-safe end time (`quietHours.ts`). Disabling quiet hours silently kept the old window (`??` treated `null` as "unchanged"); fixed. The preferences page now saves the browser's time zone with the window.
  - *Retries.* The consumer read `x-retry-count` from headers while the republish wrote `retryCount` into the body, `nack(requeue=false)` dead-lettered a copy on every failed attempt, the delayed republish lived in an in-process `setTimeout`, and a malformed message crashed the worker inside that timer. Now `processDelivery()` claims the delivery row (lease + `attempts` fencing), retries through outbox rows with exponential backoff (5 attempts, `DELIVERY_MAX_ATTEMPTS`), defers without spending an attempt when the breaker is open, dead-letters only exhausted or malformed messages, and skips cancelled/duplicate deliveries. Consumers are re-attached after a reconnect; a sweeper re-enqueues expired leases. Queue arguments were deliberately left unchanged.
  - *Aggregate status race.* Each channel worker read all delivery rows and wrote the aggregate without a lock; the slower writer could store `partial` after both succeeded. Recomputed under a `FOR UPDATE` lock on the notification row.
  - *Idempotency was dead code* — the route never read `Idempotency-Key`. It is now wired, scoped per caller (keys were global, so one user could receive another's cached result), bound to a body fingerprint (`422` on mismatch), `409` while in flight, stores only `2xx`, and uses compare-and-set Lua for completion/release. Content dedup was `GET` then `SETEX` (racy) on a 32-bit hash that could collide across users; now `SET NX` on `dedup:{user}:{sha256}` and released when nothing is created. Rate limits were consumed channel by channel (a request rejected on email had spent push budget) with `INCR` and `EXPIRE` as separate calls; now one all-or-nothing Lua script, applied after preference filtering. Statuses: `202` queued/scheduled, `429` + `Retry-After`, `400`/`404` for bad input instead of `400` for everything.
  - *Authorization.* Any logged-in user could send email/SMS to any user via `body.userId` (now admin-only); open/click events could be written against anyone's notification (now recipient or admin, and a channel the notification used); a demoted admin kept admin rights for up to 24 h through the cached session (role changes now evict the user's session keys); two concurrent campaign starts both fanned out (now an atomic `UPDATE … WHERE status IN ('draft','scheduled')`, `409` for the loser) and each recipient carries a unique `dedupe_key = campaign:{id}:{user}`.
  - *Admin "queue depth"* read Redis lists nothing wrote; it is now the real backlog from `delivery_status`, plus `outboxLagSeconds`.
  - *Frontend:* one `Idempotency-Key` per submitted draft (reused on resubmit), outcome announced in an `aria-live` region, errors shown (`429` as a "try again in N seconds" message).
  - *Tests and verification:* vitest added (`~4.0.18`, 25 tests). The relay and handler were driven against the same database with an in-memory publisher (priority order, duplicate skipped, retry → delivered, exhaustion → dead-letter, lease reaped, stale write fenced). ## Open Questions

1. 13 queues for 3 channels × 4 priorities is already awkward. At what channel count does this flip to being better served by RabbitMQ priority queues (one queue, `x-max-priority`) despite the head-of-line risk?
2. Preferences are applied only at accept time. Should the worker re-check the cached opt-out right before sending, so a quiet-hours-deferred message can't outlive the user's consent? (One Redis read per delivery.)
3. Dead letters are recorded as `notification_events` rows and the delivery is marked `failed`, but there is no replay path. Since claims are idempotent, replay could simply reset the delivery to `retrying` and insert an outbox row — admin action, or automatic after the breaker closes?
4. Campaign sends and transactional sends share the same worker pool per channel, and the fan-out itself runs inside the HTTP request. Should campaigns become a resumable background job (the per-recipient `dedupe_key` already makes reruns safe) with dedicated low-priority workers?
5. The relay polls every 200 ms. Is `LISTEN/NOTIFY` worth adding for critical sends, or is the poll interval already inside the latency budget at this scale?
