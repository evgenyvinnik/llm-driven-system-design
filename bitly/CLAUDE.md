# Bitly (URL Shortener) — Development with Claude

## Project Context

A URL shortener is deceptively small: two endpoints, one table. What makes it a real system-design problem is the **read/write asymmetry**. Creating a short link is rare and can afford a database write, a uniqueness check, and a hundred milliseconds. Following one is the opposite — it happens thousands of times more often, it sits directly in a user's page load, and it must answer in single-digit milliseconds or the link feels broken. Every decision in this project is downstream of that ratio.

The second problem is generating unique short codes without coordination. Three API instances must never hand out the same code, and the obvious answers all fail in interesting ways: a shared counter serializes every creation through one row; hashing the long URL means two users shortening the same link collide (and gives an attacker an oracle); random-with-retry degrades as the space fills. This project uses a **pre-generated key pool** — codes are minted in bulk ahead of time and leased in batches to instances, so the uniqueness question is answered once, offline, instead of on every request.

Third, analytics is a write amplifier sitting on the hottest path in the system. Every redirect wants to record a click, but an `INSERT` in the redirect handler makes the fast path as slow as the slowest write and couples link resolution to analytics availability. Decoupling the two is what RabbitMQ is doing here.

**Learning goals:** pre-generated key pools with batch leasing, read-through caching for a read-dominated workload, async event ingestion via a queue with a synchronous fallback, the 301-vs-302 trade-off, and circuit-breaking the database.

## Architecture at a Glance (what actually runs)

|-----------|------|------|--------------|
| **Express API** (`backend/src/index.ts`) | **3000** | `/api/v1/{auth,urls,analytics,admin}` plus the root-mounted `/:shortCode` redirect | Redirects mount at `/` *after* the API routes so `/api/...` can't be swallowed as a short code |
| **Analytics worker** (`backend/src/workers/analytics-worker.ts`) | — | Consumes `click-events`, prefetch 10, manual ack; idempotent insert keyed by `event_id`; delayed retries via `click-events.retry`, then `click-events.dlq` | Separate process so a slow write path cannot back up redirects; `dev:worker1/2` run two in parallel |

| **Valkey 7** | 6379 | `url:{code}` → `{url, expiresAt}` (TTL ≤ 24h and ≤ time left), `url:neg:{code}` (60s), `url:inv:{code}` invalidation guard (10s), `session:{token}` (TTL = session's remaining life), `idempotency:{user}:{key}`, `rl:{limiter}:{ip}` | The redirect fast path; a cache miss is always recoverable from Postgres |
| **RabbitMQ 3** | 5672 / 15672 | Durable `click-events` (arguments unchanged), `click-events.retry` (dead-letters back after a per-message delay), `click-events.dlq`; publisher confirms | Buffers the write amplification; management UI at 15672 |

## Key Design Decisions

### 1. Pre-generated key pool leased in batches of 100, not a counter or a hash
`fetchKeyBatch()` claims a batch with `UPDATE key_pool … WHERE short_code IN (SELECT … WHERE is_used = false AND allocated_to IS NULL LIMIT 100 FOR UPDATE SKIP LOCKED)`, stamping `allocated_to = SERVER_ID`. Keys then live in a process-local array and are popped without touching the database at all; a refill fires when the cache drops below 50. The alternatives each break somewhere specific. A shared counter (base62-encoded) makes every URL creation contend on one row, so creation throughput is bounded by a single row's lock, and the codes are sequential — meaning anyone can enumerate every link ever created by counting. Hashing the long URL means two users shortening the same target get the same code and therefore share analytics, and it lets an attacker test whether a given URL has been shortened. Random-with-retry works while the space is empty and degrades as it fills, with no bound on retries. The pool answers uniqueness once, in bulk, offline. `FOR UPDATE SKIP LOCKED` is what makes concurrent instances refill without blocking each other — they skip rows another instance is already claiming instead of queueing behind it. The cost is a three-state lifecycle (`available` → `allocated` → `used`) that has to be monitored, plus lease bookkeeping: a lease lasts `KEY_LEASE_TTL_MS` (60 min), instances retire local keys 10 minutes before that, and `reclaimStaleKeys()` hands unused expired leases back to the pool (see the 2026-10-10 log entry). The lease TTL is a cluster-wide contract — every instance must use the same value.

### 2. 302 rather than 301, accepting permanently higher load to keep analytics
`res.redirect(302, longUrl)`. A 301 is the semantically correct answer — the mapping really is permanent — and browsers cache it aggressively, which would make repeat visits cost us literally nothing. That is exactly the problem: a cached 301 means the second and every subsequent click by that browser never reaches us, so click counts silently under-report by an amount that varies with browser cache behavior and is unmeasurable from our side. For a product whose entire value beyond redirection *is* the analytics, undercounting by an unknown factor is worse than serving more traffic. So we take the load: every click is a request, forever. That is a permanent, structural cost accepted for data fidelity, and it's the single biggest reason the Redis cache in decision 3 exists.

### 3. Redis read-through on the redirect path, and the click write pushed off it entirely
The redirect handler resolves the code through `resolveShortCode()` (Redis first, then a single-flight Postgres read on a miss), back-filling the cache for at most 24 hours and never past the link's expiry. Then the click record is published to RabbitMQ *after* the response is already on its way. Doing the analytics insert inline would put a durable write in front of every redirect — the fast path would inherit the write path's latency and, worse, its availability: a slow or full database would turn link resolution into a timeout. Publishing to a queue makes the redirect's cost a cache read plus a fire-and-forget enqueue. The trade-off is that click counts are eventually consistent — a user who clicks and immediately opens the analytics page may not see their own click — and if the process dies between responding and publishing, that click is simply lost. Losing an occasional click is acceptable; losing a redirect is not. There is a deliberate fallback: if RabbitMQ is down, or the broker does not confirm the publish within 5 seconds, the click is inserted directly via `recordClickSync()`. Every event carries an `event_id` assigned at the redirect, so a late confirm plus the fallback, or a broker redelivery, still records it once.

### 4. Custom codes are validated against `urls` *and* `key_pool`, not just `urls`
`isCodeAvailable()` rejects reserved words (`admin`, `api`, `login`, `health`, …) and then checks both tables. Checking only `urls` looks sufficient and isn't: a code sitting unused in the pool would pass validation, get claimed as a custom code, and then be handed to some instance later as a "fresh" pool key — producing a collision on `urls.short_code` at insert time, long after the user was told their custom code was available. Checking the pool closes that. It also means custom-code validation costs two indexed lookups instead of one, and there is still a narrow race between the check and the insert that only the unique constraint actually closes. The reserved-word list matters for a subtler reason: the redirect router is mounted at `/`, so without it a user could claim the code `api` and shadow a real route.

### 5. Database queries run behind a circuit breaker; the cache does not
`utils/database.ts` wraps `query` in an Opossum breaker exposed on the health endpoint. Postgres is the dependency whose failure mode is *slow*, not *down* — connections that hang rather than refuse, which is the case where retries make things worse by holding connections and exhausting the pool while the database recovers. Failing fast when the error rate crosses the threshold sheds load and lets it recover. Redis is deliberately left unbreakered because its failure is already handled by design: a cache miss falls through to Postgres, so an unavailable Redis degrades performance rather than correctness, and a breaker on it would add a failure mode where we refuse to even *try* the cache. The cost of the database breaker is that an open circuit rejects requests that might have succeeded — acceptable, because a rejected redirect is an error the user can retry, while a wedged connection pool takes the whole service down.

## Current State

Runs end to end: `docker-compose up -d` (Postgres, Valkey, RabbitMQ), backend on 3000, at least one analytics worker, frontend on 5173. Implemented: URL shortening with pool-allocated or custom codes (insert and key mark-used in one transaction, bounded retry on a unique violation), optional `Idempotency-Key` on creation (replay, 409 while in flight, 422 on a different body), key leases that expire plus a startup/periodic reaper, expiration enforced on cache hits as well as misses, cache invalidation on every lifecycle write (owner update/delete, admin deactivate/reactivate, expiry cleanup), a 60-second negative cache and per-instance single-flight for misses, 302 redirects with `Cache-Control: private, no-store`, click tracking (referrer, device type, IP) through RabbitMQ with publisher confirms and a sync fallback, exactly-once click persistence keyed by `event_id`, delayed retries and a dead-letter queue in the worker, owner-or-admin analytics, session auth with bcrypt (cache TTL bounded by the session), Redis-backed rate limits with `RateLimit` headers, Helmet, Prometheus metrics, structured Pino logging, an Opossum breaker on the database, graceful shutdown, and an admin dashboard with stats, URL management, user management, and a key-pool tab.

**Tests:** `cd backend && npm test` runs 132 offline vitest unit tests (Redis, Postgres, and amqplib mocked; the RabbitMQ consumer is exercised against an in-memory fake channel).

**Seeded logins:** `alice@example.com` and `bob@example.com`, both `password123` (verified against the seeded hash). `admin@bitly.local` is seeded with the `admin` role but **its hash matches no known password** — see the repair log; use `alice` unless you first reset the admin hash.

Not built: no local in-memory LRU in front of Redis (the redirect is one Redis round trip today), no sharding or read replicas, no malicious-URL screening, no DLQ replay tooling (dead letters are inspected and shovelled back by hand in the management UI), no tests against a live RabbitMQ, and no frontend tests.

  - *Creation middleware never ran.* `app.post('/api/v1/urls', createUrlLimiter, idempotencyMiddleware)` was registered after the urls router had already answered, so neither ran. Both now sit on the router's `POST /` (limiter → `optionalAuth` → idempotency). Idempotency only keys off an explicit `Idempotency-Key` (the body-fingerprint fallback silently merged intentional duplicates), is scoped by user, claims with `SET NX EX 60` (409 + `Retry-After` while in flight), hashes the body (422 on reuse with a different body), and finishes the claim with a compare-and-set so a request never overwrites a claim it lost. It fails open when Redis is down.
  - *Creation was not atomic.* The `urls` insert and `key_pool` mark-used now share one transaction; a 23505 on a generated code retires that key and retries with a fresh one (max 3, then 503). The pool-empty fallback uses `crypto.randomInt`. Custom codes are 4–10 characters to match `VARCHAR(10)`, and `metrics`, `ready`, `dashboard` are reserved. Service errors carry an HTTP status (`utils/errors.ts`), so infrastructure failures are 500s instead of 400s.
  - *Stranded leases.* Batches are stamped before the lease query; local keys are discarded 10 minutes before the 60-minute lease TTL; `reclaimStaleKeys()` marks pool rows already present in `urls` as used and releases unused leases older than the TTL, at startup and every 5 minutes. Refills are coalesced and run in the background unless the local cache is empty. The dead Redis `keyPoolCache` was deleted.
  - *Expired links kept redirecting from cache.* The cache value is now `{url, expiresAt}` with TTL = min(24h, time left); hits enforce expiry; expired links are never cached; legacy plain-string values read as a miss. Every lifecycle write invalidates and sets a 10-second guard key that stops in-flight lookups from writing the old row back. The duplicated lookup in `routes/redirect.ts` is gone in favor of `resolveShortCode()`.
  - *IDOR on analytics.* Any logged-in user could read any link's analytics, including raw IPs. Now owner-or-admin (403 otherwise). The admin hourly chart grouped by hour-of-day without the date; it now uses `date_trunc('hour', clicked_at)`.
  - *Click double counting and poison loops.* `click_events.event_id` (UUID, unique index, added with `ADD COLUMN IF NOT EXISTS`) is assigned at the redirect; the worker and the sync fallback insert with `ON CONFLICT (event_id) DO NOTHING` and bump `click_count` only when a row was inserted, in one transaction. Publishing uses a confirm channel; a nack or 5s timeout falls back to the sync insert, and a full socket buffer waits for `drain` (bounded). Failures are re-published to `click-events.retry` with `x-retry-count` and a per-message expiration (10s) that dead-letters back to `click-events`; after 5 attempts, or immediately for malformed JSON and SQLSTATE class 22/23 errors, they go to `click-events.dlq`. The main queue's arguments were deliberately left unchanged (changing them makes `assertQueue` fail with PRECONDITION_FAILED on existing brokers). The consumer is re-attached after every reconnect, and reconnects retry with backoff.
  - *Sessions.* Cache TTL is the session's remaining lifetime instead of a fresh 7 days per fill; cache reads fall back to SQL on Redis errors; logout evicts Redis, deletes the SQL row, then evicts again, and returns 503 (cookie still cleared) if revocation could not be confirmed.
  - *Per-process rate limits.* `rate-limit-redis` 6.x requires express-rate-limit 8.6+, so instead of a major upgrade a small Redis fixed-window store (Lua `INCR` + `PEXPIRE`) plugs into the existing express-rate-limit 7 with `draft-7` headers; it skips limiting while Redis is down and gives up after 250 ms.
  - *Shutdown* stops HTTP admission, stops the reaper, waits for in-flight click dispatches, then closes RabbitMQ, Postgres, and Redis (forced exit after 10s). `init.sql` now only populates the key pool when fewer than 1,000 keys are available, so re-running it is safe.
  - *Frontend:* one `Idempotency-Key` per submitted draft (reused on retry of the same draft), inputs locked while submitting, URL store reset on login/logout/session loss (in-flight responses dropped), analytics fetches aborted on close, visible clipboard failures, and inactive/expired badges in the link list.
  - *Tests:* vitest added (pinned `~4.0.18`: npm 10.9 crashes with "Cannot read properties of null (reading 'edgesOut')" resolving vitest 4.1's optional peers). Verified against real Postgres 16 and Redis with RabbitMQ absent: idempotent replay/409/422, 2-second expiry 404s despite being cached, deactivation and reactivation take effect immediately, 25 concurrent redirects produce exactly 25 events, a mid-burst SIGTERM loses no clicks.

## Open Questions

1. Rate limiting is per-IP on creation (now shared across instances through Redis). Authenticated users behind one corporate NAT share a budget; anonymous users behind a rotating proxy have none. Is per-user-when-authenticated / per-IP-otherwise the right split, or does that just move the abuse to unauthenticated creation?
2. A local LRU in front of Redis would remove a network hop from the hottest path, but a deactivated URL would keep redirecting from each instance's memory until its TTL lapsed — the Redis invalidation guard does not reach process memory. Is the hop worth eliminating given the correctness cost, or is that only worth it above some RPS the project will never see?
3. Click analytics currently aggregate on read. At what click volume does that stop working, and is the answer pre-computed rollup tables in Postgres or a real column store — given the queue that would feed either is already in place?
4. Idempotency and rate limiting fail open when Redis is down: a client retrying during an outage can create a duplicate link, and creation is unlimited. Should creation fail closed (503) instead when the client sent an `Idempotency-Key`?
5. Dead letters need a replay path. The consumer is idempotent, so shovelling `click-events.dlq` back into `click-events` is safe — should that be an admin action rather than a manual step in the management UI?
