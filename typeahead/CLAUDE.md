# Typeahead — Development with Claude

## Project Context

Autocomplete has a latency budget measured against human typing, not against a page load. A suggestion list that arrives 200ms after the keystroke is already describing a prefix the user has moved past. And because the request fires on *every* keystroke, the read volume is roughly "characters typed per second across all users" — a query pattern where the average request must be cheap, not just the p50.

That constraint rules out the obvious implementation. `SELECT phrase FROM phrases WHERE phrase LIKE 'ca%' ORDER BY count DESC LIMIT 10` is correct and unusable: even with a B-tree supporting the prefix scan, the database is ranking a candidate set whose size is inversely proportional to prefix length — the shortest, most common prefixes are the most expensive queries, and short prefixes are exactly what people type first.

So the shape of the system is: precompute the answer at every possible prefix, hold it in memory, and spend the rest of the effort on caching layers and on making the client not send requests it doesn't need. The interesting engineering isn't the trie — it's everything wrapped around it: what gets cached where, what can be cached at all (personalized ranking can't), and how phrase-count write volume gets collapsed before it reaches Postgres.

**Learning goals:** trie construction with precomputed top-k, multi-layer caching from service worker to Redis, multi-factor ranking blending popularity/recency/personalization/trending, buffered write aggregation, and client-side debounce/ordering/abort discipline.

## Architecture at a Glance (what actually runs)

| Component | Port | Why this one |
|-----------|------|--------------|
| **API server** (`backend/src/index.ts`) | **3000** | Express, single process; the trie lives in this process's heap, so the server *is* the index. `dev:server1/2/3` run 3001–3003 for multi-instance experiments |
| **PostgreSQL 16** | 5432 | Durable source of truth for `phrase_counts`, `query_logs` and `filtered_phrases` — the trie is rebuilt *from* it at startup. `user_history`, `analytics_summary` and `trending_snapshots` exist in `backend/src/db/init.sql` (the last two with seed rows), but no code reads or writes them |
| **Valkey (Redis)**, via ioredis | 6379 | Suggestion cache (60s), 5-minute trending windows, the `trending_queries` zset, blocked-phrase set, idempotency records, and per-user history for personalization (`user_history:{userId}`, 90-day TTL; the only copy, so a Redis flush loses it) |

There is no separate index server and no message queue — the trie is constructed in `initialize()` when the process starts and mutated in place. `backend/src/data-structures/trie.ts` is the core; `services/suggestion-service.ts` (cache + trie lookup + fuzzy), `services/ranking-service.ts` (five-factor scoring), `services/aggregation-service.ts` (buffered writes, filtering, trending windows). Shared middleware in `backend/src/shared/`: `cache-headers.ts` (Cache-Control strategies + ETag), `rate-limiter.ts`, `circuit-breaker.ts`, `idempotency.ts`, `logger.ts`, `metrics.ts`. Routes are `/api/v1/suggestions`, `/api/v1/analytics`, `/api/v1/admin`.

Frontend is React + TanStack Router + Zustand + Tailwind. The search page runs `SearchBox` → `stores/search-store.ts` → `services/api.ts` (`useDebounce` plus a request sequence number and a prefix guard). Four further typeahead widgets (`components/widgets/`: `CommandPalette`, `InlineFormTypeahead`, `MobileTypeahead`, `RichTypeahead`) run over one `useTypeahead` hook, with an IndexedDB layer (`db/database.ts`), on the lazy `/widgets` demo route linked from the nav. Client caching: `services/cache.ts` (in-memory LRU with TTL) and `src/sw.ts` (service worker, production builds only: network-first navigations, versioned caches, API cache capped at 200 entries with 24h maximum staleness). `services/performance.ts` exists but no route imports it; `services/prefetch.ts` was deleted because nothing imported it. Vite proxies `/api` → `localhost:3000`.

## Key Design Decisions

### 1. Top-k is precomputed at every trie node, not computed at query time

`Trie.insert()` walks the phrase character by character, then updates the sorted top-10 of *every node along the path, root included*, bottom-up. When a count goes down at a node whose list is full, that node's list is rebuilt from its own phrase plus its children's top-k lists (each child list is already its subtree's top-k), since the full list may have evicted phrases that now outrank it; `remove()` repairs ancestors the same way and prunes dead nodes. `getSuggestions()` then walks the prefix and returns `node.suggestions` — no subtree traversal at all, O(prefix length) with a tiny constant — and `getSuggestions('')` returns the global top-k from the root. `getStats()` is O(1) from counters maintained on insert/remove.

The alternative is storing counts only at terminal nodes and collecting the subtree at query time. That fails at exactly the wrong end of the input distribution: for a one-character prefix like "a", the subtree under that node is a large fraction of the entire corpus, so you traverse it all and then sort it, on the request that arrives most often. Query cost would be inversely proportional to how much the user has typed, meaning latency is worst at the moment the user has the least patience.

What we pay is memory and write cost. Every node on the path stores up to 10 suggestion objects, so memory is roughly `nodeCount × k` rather than `phraseCount`, and it's dominated by short prefixes shared across many phrases. Insert is `O(L × k log k)` — for each of L characters we do a linear scan for an existing entry, a sort, and a truncate. That's fine because inserts are batched every 30 seconds (decision 3) and reads happen per keystroke; the asymmetry is the entire justification.

### 2. The cache stores *unranked* suggestions; ranking runs after every cache read

`getSuggestions()` checks Redis first, and on a hit it still calls `rankingService.rank(cached, context)` before returning. The cached value is the trie's raw top-k, not the response.

This is the design point that makes caching possible at all. Ranking blends popularity (0.30), recency (0.15), personalization (0.25), trending (0.20), and match quality (0.10) — and personalization reads *this* user's history (the Redis key `user_history:{userId}`). If the cache held the final ranked response, the key would have to include the user ID, which shatters the cache into one entry per user per prefix and destroys the hit rate that makes the cache worth having. By caching the prefix→candidates step (identical for everyone) and applying the user-dependent step after, one cached entry serves every user typing that prefix.

The trade-off is that the expensive part isn't cached: ranking does a Redis lookup per suggestion for the personal score and another for the trending boost, so a cache hit still costs `2k` Redis round trips (fetched in parallel, each raced against a 30ms timeout, and skipped while Redis is disconnected, so a Redis outage drops the personal/trending signals instead of failing the request). The 60-second TTL is also a deliberate staleness bound rather than an invalidation strategy — admin trie rebuilds clear the whole cache and admin add/remove/filter/unfilter call `invalidatePhrase()` (deletes every prefix key of the phrase plus the popular list), but ordinary count updates from the flush just wait out the TTL. Keys are `suggestions:prefix:<normalized prefix>` and `suggestions:popular`, so no prefix can collide with the popular list; a prefix keeps one trailing space ("java " completes the next word, not "javascript") and gets its own key. Cache reads and writes are skipped while Redis is not ready, a read slower than 50ms counts as a miss, and nothing is cached while the trie is empty.

### 3. Query counts are buffered in memory and flushed every 30 seconds

`AggregationService` keeps a `Map<query, {count, firstSeen}>` (bounded at 50,000 distinct phrases), increments it per completed search, and flushes to Postgres plus the trie on a 30-second timer. The buffer is fed by `POST /api/v1/suggestions/log` — a selected suggestion or a submitted query — not by keystrokes. Only the `phrase_counts` upserts are buffered: each logged search still does a blocklist check (Redis set, then a Postgres SELECT) and one `query_logs` INSERT.

Writing a `phrase_counts` upsert per logged search would make write volume track aggregate search volume, with the hottest phrases contending on the same rows. The buffer collapses repeated searches into one upsert per distinct phrase per window, which for a popular query turns thousands of writes into one.

There's a second reason the buffer has to exist: the trie is updated from these counts, and `insert()` re-sorts the suggestion list at every node on the path. Applying that per search would put a `O(L × k log k)` mutation in the request path. The flush inserts the *stored* total returned by the upsert (not a delta), so the trie matches the database, and it skips phrases that are filtered (`is_filtered` in `phrase_counts`, or in the Redis blocked set).

What we give up is real: a crash loses up to 30 seconds of counts (SIGTERM/SIGINT run `await aggregationService.stop()`, which does a final flush before the pools close; a failed upsert requeues the batch), and the buffer is per-process, so with multiple instances the same phrase accumulates separately in each and lands as several independent upserts. `POST /log` is not deduplicated either. Counts are approximate by construction — acceptable, because they feed a *ranking*, not a billing system.

### 4. Trending is a separate signal from popularity, computed over 5-minute windows

`updateTrending()` does `ZINCRBY trending_window:{floor(now/300000)}` with a 1-hour expiry, and `aggregateTrendingWindows()` recomputes `trending_queries` every 30 seconds by unioning the last 12 windows with weights `0.9^age` and subtracting the `blocked_phrases` set (`ZDIFFSTORE`), which the ranker reads as a 0.20-weight boost. The age weighting *is* the decay; there is no separate decay timer, and a phrase stops trending once its windows expire. Phrases an admin removed with `DELETE /admin/phrases/:phrase` are still counted but not added to the windows.

Folding trending into the popularity count would be simpler and wrong. Popularity is cumulative and slow — a phrase that has been searched a million times over two years dominates, permanently, and nothing new can ever surface. Trending is a *rate*, and rates need a window. Five minutes is short enough that a spike registers within one flush cycle; keeping twelve of them means the boost reflects the last hour while individual windows expire on their own without a cleanup job.

The cost is that this is a second counting system with its own keys, its own decay, and its own failure mode — and the two can disagree, which is exactly what the 0.30/0.20 weight split is arbitrating.

### 5. The client debounces at 150ms, orders responses by sequence number, and aborts as an optimization

`SearchBox` (through `useDebounce`, which exposes `cancel()` for clear and select) and `useTypeahead` wait 150ms after the last keystroke (the command palette passes 100ms). Every search takes a sequence number (`searchSeq` in `stores/search-store.ts`, `requestSeq` in `useTypeahead`), and any success, error or `finally` from a request that is no longer the latest is ignored. The previous request of the same input is also aborted, scoped per input so two widgets never cancel each other.

Debounce alone isn't sufficient, and the reason is subtle: a slow request for "co" can resolve *after* a fast request for "coff", overwriting the correct suggestions with stale ones, and the user sees the list flicker backwards. Abort alone doesn't fix it either: a newer request answered synchronously from the memory cache never reaches the network, so it cannot be relied on to cancel the older one, and a late settle can still land after a cleared input or a selection. The sequence check makes the ordering guarantee independent of the network; abort just saves the wasted request.

HTTP caching depends on who is asking. Anonymous suggestion responses carry `Cache-Control: public, max-age=60, s-maxage=60, stale-while-revalidate=300` plus a weak ETag computed over stable content (it excludes `responseTimeMs`, timestamps and `meta.cached`). The app always sends `userId`, so its requests get `private, no-cache` instead — the browser may store them but revalidates every time (a 304 when unchanged), because personalized ranking changes as soon as the user logs a search — and the client fetches them with `cache: 'no-cache'` as well. Errors and degraded (circuit-breaker fallback) responses get `no-store` and no ETag.

## Current State

Runs end to end with no login — `auth.enabled` is `false` in the screenshot config because this system has no user accounts; `userId` is just an optional query parameter used to look up personalization history.

Implemented: trie with precomputed top-10 built from `phrase_counts` at startup, prefix suggestions, **fuzzy matching** (`?fuzzy=true` on `GET /api/v1/suggestions`: `Trie.findFuzzy()` walks the trie as a bounded DFS carrying one prefix edit-distance row per node — Damerau/OSA, so an adjacent swap costs 1 — with an edit budget of 0/1/2 by prefix length, a 20,000-node cap, no fuzzy work above 50 characters, and a 0.2 score penalty per edit), popular and trending endpoints, per-user history (atomic Lua update, most recent first, max 100), query logging with low-quality filtering (too short, too long, all digits, control characters, keyboard smash = a vowelless word of 6+ letters or a run of 7 adjacent keys on one QWERTY row, 5+ repeated non-digit characters) and a blocklist checked in both the Redis `blocked_phrases` set and `filtered_phrases` (either can block; it fails closed only when neither can be read), five-factor ranking, buffered aggregation with 30s flush and 30s trending recomputation, an admin surface (trie stats, rebuild, add/remove phrases, add/remove filters, cache clear, status) where mutations deduplicate on an explicit `X-Idempotency-Key`, per-route rate limiting keyed on the socket IP, HTTP cache headers with weak ETags, Prometheus metrics including trie stats, cache hit/miss, filtered-query counts and flush duration, and structured logging (query text truncated, user ids pseudonymized) with an audit logger.

Validation: a `q` over 200 characters returns an empty list and a logged `query` over 200 gets 400, ids are limited to 100; `limit`/`offset` are clamped and fall back to defaults. `POST /log` answers 200 with `accepted`/`reason`, and only accepted searches go into the user's history. Admin add never lowers a count (stored count = max(existing, requested)), re-adding a removed phrase restores it, and a filtered phrase gets 409. `DELETE /admin/phrases/:phrase` keeps the row with `is_filtered = true` (still counted, never back in the trie or trending); `DELETE /admin/filter/:phrase` restores the phrase with its stored count.

Startup and shutdown: `/health/ready` is 503 until the trie has loaded (and whenever Redis or Postgres is unreachable); the trie load retries with backoff until Postgres is reachable; aggregation starts after the load, and the blocked set is resynced from `filtered_phrases` on start and on every Redis reconnect. Env vars beyond the connection settings: `CORS_ORIGINS` (comma-separated, default `http://localhost:5173`) and `TRUST_PROXY` (unset by default, so `X-Forwarded-For` is ignored).

Degradation: one circuit breaker wraps the suggestion lookup (100ms timeout, opens at 30% failures over at least 10 calls, retries after 5s); its fallback is an empty list marked `meta.degraded` and sent with `no-store`. Redis is not behind it: with Redis down, suggestions skip the cache and come from the trie with personal/trending signals at 0, `/log` still works, and `/trending` returns `[]`.

Frontend: a search page with settings and a trending list (entries are buttons that run a search), an admin dashboard with overview/analytics/management tabs (the management tab can add a filter but has no filter list or removal UI), the four `useTypeahead` widgets on `/widgets`, an in-memory LRU cache, and a service worker. `npm run lint` and `npm run build` pass.

Known gaps: `services/performance.ts` is not imported by any route. (During a Redis outage `/trending` returns an empty list marked `meta.degraded` and sent `no-store`, and `POST /admin/cache/clear` answers 503 instead of claiming success.)

**Single-node by design.** The trie is one in-process object, so the "sharding by first character" that the architecture doc describes is not implemented — `suggestion-service.ts` says as much in its header comment. Running `dev:server1/2/3` gives you three independent tries with three independent aggregation buffers, which diverge. Also not implemented: nginx load balancing, A/B testing of ranking weights, and WebSocket suggestion streaming.

## Open Questions

1. The trie is rebuilt from Postgres only at process start, and incremental inserts happen in one process's heap. With `dev:server1/2/3` running, three tries diverge within a minute. Is the fix a shared serialized trie in Redis that instances reload periodically, or does each instance need to consume a shared change log?
2. A cache hit still costs `2k` Redis round trips because personalization and trending are applied per suggestion after the cache read. Should the personal-history set and trending zset be fetched once per request instead of once per suggestion — and does that just move the cost rather than remove it?
3. The ranking weights (0.30/0.15/0.25/0.20/0.10) were chosen by hand and have never been evaluated against anything. Without click-through data there's no ground truth — what's the minimum instrumentation that would make these tunable rather than decorative?
4. `Trie.remove()` now prunes dead nodes and refills each ancestor's top-k from its children, but `phrase_counts` keeps every removed or filtered row forever (counts keep accruing while `is_filtered = true`). Should removed phrases age out, and should `DELETE /admin/phrases` have a list/undo UI rather than only the filter endpoints?
