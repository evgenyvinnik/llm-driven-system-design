# Web Crawler — Development with Claude

## Project Context

A distributed web crawler: seed it with URLs, and a pool of workers fetch pages, extract links and metadata, and feed newly-discovered URLs back into a shared frontier — all while respecting robots.txt and per-domain crawl delays. The core hard problem is the **URL frontier**: a queue that must be prioritized, deduplicated, politeness-throttled per domain, and safely shared across crashing workers, without ever crawling the same URL twice or hammering one host.

**Learning goals:** priority-queue frontier design, exact deduplication at scale, distributed politeness (one crawler per domain), and crash-safe work distribution across stateless workers.

## Architecture at a Glance (what actually runs)

Matches `docker-compose.yml` (Postgres, Valkey, an API container, and three worker containers) and `backend/package.json`:

| Store | Client | Role | Why this one |
|-------|--------|------|--------------|
| **PostgreSQL 16** | `pg` | Durable frontier state (`url_frontier` with status), crawled-page metadata, domains + robots cache, crawl stats | ACID + queryability: inspect/recover/reprioritize the queue, which a log-based queue can't do |
| **Redis / Valkey** | `ioredis` | Three priority sorted-sets (high/medium/low), the `VISITED_URLS` dedup set, per-domain crawl locks, live counters, sessions | O(1) dedup + fast priority pop on the hot path; self-expiring domain locks |

**No message queue** — the frontier *is* the queue, split across Redis (fast) and Postgres (durable). One Express **API/dashboard** server + **three worker processes** (`backend/src/worker.ts`, run as `webcrawler-worker-1/2/3`). Key deps: `cheerio` (HTML parse), `robots-parser` (politeness), `cockatiel` (retry/circuit-breaker/timeout in `shared/resilience.ts`), `express-session` + `connect-redis` (admin auth), `helmet`/`compression`/`express-rate-limit`, `prom-client`, `pino`. **Frontend:** React 19 + TanStack Router + Zustand + Tailwind dashboard that polls stats.

## Key Design Decisions

### 1. Hybrid frontier: Redis priority queues + PostgreSQL durability
`addUrl` writes the URL to `url_frontier` with `ON CONFLICT (url_hash) DO NOTHING` *and* pushes its hash onto one of three Redis sorted-sets by priority. The sorted-set score is the URL's **earliest eligible time**, so retry backoff is just a future score. `getNextUrl` reads eligible hashes high→medium→low, batch-loads their rows, wins the domain lock, and claims with a conditional `UPDATE ... WHERE status='pending'`. Trade-off: the two stores are eventually consistent, so Postgres arbitrates every claim, and `recoverStaleUrls` / `rehydrateQueues` repair Redis when it's missing entries. Chose this over pure-Postgres `FOR UPDATE SKIP LOCKED` to keep the hot dequeue off the priority index.

### 2. Exact dedup via Redis SET (not a Bloom filter)
Each URL is normalized then SHA-256 hashed; `addUrl` checks membership in the Redis `VISITED_URLS` set (`SISMEMBER`, O(1)) and the Postgres `url_hash` UNIQUE index backstops it. Trade-off: exact dedup means zero false negatives (we never skip a real page), but the set grows unbounded — at 10B URLs it's ~640GB. A Bloom filter is the production answer (10× less memory, ~0.1% false positives); exact is correct and simple at the 100K-URL learning scale.

### 3. Politeness = per-domain Redis lock, not a global rate limiter
Before crawling, a worker runs `SET crawler:domain:{d}:lock {workerId} NX PX {crawlDelayMs}`. Winning the lock is permission to crawl that domain; the TTL equals the domain's crawl-delay (max of operator override and robots.txt / 1s default), so the lock self-releases and the next fetch can't happen until the delay elapses. It does **not** provide worker exclusivity (the TTL is ~1s, a fetch can take 30s) — the conditional claim does. Retries re-acquire the lock; redirects are re-enqueued rather than followed, so every request to a host goes through the gate. A second, looser lock on the domain's **resolved IP** (`crawler:ip:{ip}:lock`, default 250ms) protects shared hosts serving many domains; CDN ranges (from env or refreshed published lists) are exempt, since their shared IPs front unrelated sites. Trade-off: domain-level (not path-level) granularity means one busy domain is a single-lane road regardless of worker count, and workers burn cycles when every eligible domain is locked; token-bucket would smooth this but adds complexity for marginal gain.

### 4. Crash recovery by leasing, not transactions
A worker marks a URL `in_progress` and crawls it outside any long transaction. If the worker dies, that row is stuck — so the API's maintenance loop (`services/maintenance.ts`, every minute) resets `in_progress` rows older than 10 minutes back to `pending` **and re-adds them to Redis**. Trade-off: a crashed worker's URL is re-crawled (at-least-once), which is fine because crawling is idempotent; the alternative (holding a DB lock for the whole fetch) would tie up connections for slow pages and turn a hung request into a stuck lock.

### 5. Metadata-only page storage
`crawled_pages` stores `title`, `description`, `content_hash`, `content_length`, `status_code`, `links_count` — **not the raw HTML body**. Content dedup is by `content_hash`. Trade-off: we can detect duplicate content and drive the dashboard without an object store; storing full pages (for a real index) is the explicit v2 that would add S3/MinIO.

## Current State

Implemented end to end: the hybrid frontier with 3-level priority, URL normalization + SHA-256 dedup (Redis set + PG unique), robots.txt fetch/parse/cache (`robots-parser`, Redis 1h TTL + PG), per-domain NX-lock politeness, three workers pulling from the shared frontier with `cheerio` link/metadata extraction, `cockatiel`-wrapped fetches (circuit breaker + one politeness-respecting retry), frontier-level retry with backoff, automatic lease recovery + Redis rehydration, redirect/robots-5xx/nofollow handling, crawler-trap limits incl. a per-domain page budget, vitest unit + integration tests, crawl-stats aggregation, per-IP politeness with CDN exemptions, public reads with admin-only mutations backed by a `users` table (admin / read-only roles, immediate session revocation served from a version-guarded Redis cache, race-safe last-admin guard, break-glass bootstrap), an append-only audit log, durable operator domain settings (block / slow-down override, rebuilt atomically from Postgres), Prometheus metrics, pino logging, and a polling React dashboard with honest freshness and stalled-vs-idle states.

Intentionally omitted: raw-HTML/content storage (S3/MinIO, v2), JavaScript rendering (Puppeteer for SPAs, v2), Bloom-filter dedup, near-duplicate/shingle detection, and any real distributed queue (Kafka/Redis Streams) — the Redis+PG frontier stands in.

- **2026-08-10 — the dashboard 404'd, the Pages table showed `undefined`, and the whole verification loop was lying.**
  1. **`/dashboard` rendered "Not Found."** The dashboard component is mounted at `/` in `router.tsx`; the screenshot config asked for `/dashboard`, which no route defines. A config error, not an app bug — but it meant the project's main screen had never been captured.

This is what made fault 2 so confusing: after fixing the route, a full harness run still showed `undefined`, because a leftover *container* was serving the old code while the harness's own backend had crashed on startup. **The verification loop was silently validating code that wasn't the code on disk.** Fixed by putting `api`, the three workers, and `frontend` behind a Compose `app` profile, so a bare `docker-compose up -d` brings up Postgres and Redis only, and `docker-compose --profile app up -d` still runs everything containerized.

A stale process or container makes the harness produce confident, wrong results — and `down -v` does not remove containers for services that have since been moved behind a profile, so they linger.

It argued "WebSocket over SSE" and "Redis Pub/Sub for stats distribution" in a codebase with **no WebSocket anywhere** (the dashboard polls `/api/stats` every 5s via `setInterval`), and praised a "shared types folder" that prevents drift when there is no `shared/` directory — the types are duplicated per side, and that duplication is precisely what caused fault 2. - **2026-11-24 — implementation review: the frontier wasn't self-healing, and politeness leaked.** Read through the crawl path end to end and fixed what didn't hold up; then wrote an opt-in integration test (`src/integration/`) that crawls a local fixture site with three workers against real Postgres/Redis — which found two more bugs the read-through missed.
  1. **Circuit breaker published OPEN on every transition.** cockatiel's `CircuitState` is a numeric enum; `state.toString()` gave `'0'`/`'2'`, which never matched `'closed'`/`'halfOpen'`, so even a reset to closed wrote `open` to Redis — with a 1h TTL. Since workers skip open domains without fetching, no breaker ever went half-open to clear it. Now mapped explicitly, TTL = break duration, deleted on close; open-circuit URLs are deferred, not failed.
  2. **Recovered leases were invisible.** `recoverStaleUrls` reset rows in Postgres only; workers dequeue from Redis, so recovered URLs were never crawled. It was also only reachable via a manual admin button. Now re-enqueues, and runs every minute alongside `rehydrateQueues` (Redis loss repair).
  3. **Rediscovery reset queue position.** `addUrl` ZADDed even when the INSERT was a no-op, resetting the score to now — the most-linked pages kept moving to the back — and counted every rediscovery as a new link. Now batched (SMISMEMBER + multi-row INSERT ... RETURNING + ZADD NX) for inserted rows only: constant round trips per page instead of ~4 per link.
  4. **Claim race.** The pending check and the `in_progress` update were separate statements; with lock TTL < fetch time two workers could claim one URL. Now a conditional UPDATE.
  5. **Every failure was permanent.** One timeout or 503 marked a URL failed forever. Added `retry_count`/`last_error`, outcome classification (transient vs permanent), and eligible-at backoff with jitter; 429 honors Retry-After.
  6. **Redirects bypassed robots/politeness** (axios followed 5 hops to any host) and links were resolved against the pre-redirect URL. Now `maxRedirects: 0`, target re-enqueued.
  7. **robots.txt 5xx = allow everything.** Now fail-closed + retry (RFC 9309); 4xx still allows. HTTPS connection failure now actually falls back to HTTP; 512 KiB cap; Crawl-delay fallback uses config, capped at 60s.
  8. **Found by the integration test:** robots.txt was ignored for every `http://` site — robots-parser was always built with an `https://` URL and returns `undefined` for other origins, which the code read as "allowed". And `extractDomain` used `hostname`, dropping ports, so `site:8080`'s robots.txt was fetched from `site:443`. Parser now per scheme; domain key is `host`.
  9. **Found by the integration test:** the in-process retry hit the host 157ms after another worker's request — retries bypassed the politeness lock. Retries now wait for the domain slot; in-process retries cut to 1 (frontier retries handle longer outages).
  10. Smaller: domain settings (`crawlDelay`, `isAllowed`) were written to Postgres but never read by workers — now published to Redis, override = max(override, robots) so it can't speed past robots.txt; tracking-param stripping; depth/URL-length/links-per-page trap limits; `<base href>`, nofollow; exact content-hash dedup skips re-enqueuing links; graceful worker shutdown waits for the in-flight crawl; `frontier/clear` also empties Redis queues; frontend `lint` script fixed for flat config; Frontier page shows retry count + last error.
- **LESSON:** the read-through found seven bugs; the end-to-end test found two more in code I had already reviewed and edited (robots-parser origin semantics, retry politeness). Library behavior at boundaries — what a parser returns for an input it doesn't handle — doesn't show up in reading, only in running. A fixture site with asserted request timings is cheap and catches exactly this class.

  1. **Admin login had never worked.** `connect-redis` v9 targets node-redis v5 (`set(key, val, { EX })`); this project passes an **ioredis** client, which sends the options object as a literal argument → `ERR syntax error` on every session write. The login handler had already responded 200, so the failure surfaced only as an unhandled error after the response (which also crashed the error handler with `ERR_HTTP_HEADERS_SENT`). No session was ever persisted, so even the existing `/api/admin/*` routes were unreachable. Pinned `connect-redis@^7.1.1` (supports ioredis); error handler now defers when headers were sent. Several other projects in the repo pair `connect-redis` v8 with ioredis and may have the same problem — not checked here.
  2. **Every mutating route now requires an admin session** (`requireAdmin`): frontier add/seed/recover/clear, stats reset, domain settings, robots refresh. Reads stay public. Login: rate-limited (10 / 15 min), session regenerated, PBKDF2 210k + `timingSafeEqual`, constant work for unknown users. Credentials from `ADMIN_USERNAME`/`ADMIN_PASSWORD` (default `admin`/`password123`, the repo standard); production refuses to start without `ADMIN_PASSWORD`/`SESSION_SECRET`. CORS is an allowlist instead of reflect-any-origin-with-credentials. `COOKIE_SECURE`/`TRUST_PROXY` added because the compose `api` runs `NODE_ENV=production` behind plain-HTTP nginx, where express-session silently drops Secure cookies — login could never have stuck in the containerized profile either.
  3. **Anonymous rate limit was 10/min while the dashboard polls 12/min** — anonymous viewers got 429s within a minute. Raised to 120/min.
  4. **Operator settings weren't durable.** Blocks and delay overrides lived only in Redis, so a Redis restart silently unblocked every blocked domain. Added `domains.crawl_delay_override` (separate from the robots `crawl_delay`), `services/domainSettings.ts` (publish + `republishAll`), and the maintenance loop republishes every minute. `/api/admin/domains/:d/reset` also now clears the Redis block key. Settings UI added to the Domains page for admins.
  5. **Per-domain page budget** (`CRAWLER_MAX_PAGES_PER_DOMAIN`, default 10,000, seeds exempt): counters in one Redis hash, lazily initialized from Postgres so a Redis restart doesn't reset budgets; `frontier/clear` resets them.
  6. **Frontend polling made trustworthy:** settle-then-schedule (no stacked requests), sequence-guarded responses, visibility pause, exponential backoff, and a freshness indicator computed from data age (the old "Live" dot pulsed green while the API was down). - **2026-11-24 (latest) — the three remaining gaps.**
  1. **Un-block sweep.** Blocks and overrides were one Redis key per domain, so the rebuild could restore missing blocks but not find *stale* ones without a SCAN over every domain's keys. Moved them into one SET (`crawler:blocked_domains`) and one HASH (`crawler:delay_overrides`), rebuilt in a single MULTI/EXEC — drift is fixed in both directions. The rebuild reads a Postgres snapshot before writing Redis, so it `WATCH`es a version counter that every publish bumps (on a dedicated connection, since ioredis multiplexes and another EXEC would clear the watch); a concurrent change aborts the rebuild rather than being overwritten. Old per-domain keys are simply no longer read; the first rebuild populates the new structures.
  2. **Per-IP politeness.** `acquirePolitenessSlot` takes the domain lock, then `crawler:ip:{ip}:lock` (`CRAWLER_IP_DELAY_MS`, default 250) for the domain's resolved IP (`dns.lookup`, cached in Redis, negative-cached 60s). IP lock taken → domain lock released so the slot isn't burned; the scan then skips other domains on that IP without touching Redis. In-process retries use the same slot. Measured with two workers on a two-domain, one-IP fixture: lock off → 12 of 25 gaps under 100ms (min 0ms); lock at 1500ms → min gap 1505ms. Default kept looser than per-domain because CDNs put unrelated sites behind shared IPs.
  3. **User accounts.** `users` table (`services/users.ts`, `routes/users.ts`): roles `admin` / `user` (read-only), PBKDF2 hashes with the iteration count encoded in the hash, async `crypto.pbkdf2` (the sync call blocked the event loop ~150-200ms per login). Sessions carry `session_version`; protected routes re-read the user by PK, so disable / role change / password reset revoke sessions on the next request. Last-admin guard runs in a transaction that row-locks all active admins — tested by firing two concurrent cross-demotions (exactly one wins). Self-demote/delete refused. `POST /api/auth/password` re-issues the caller's session and kills the others. `ADMIN_USERNAME`/`ADMIN_PASSWORD` now only bootstrap — or restore — an admin when none is active (break-glass). Admin page: Users panel + change-password form; read-only accounts get an Account page instead of the login form.
- **LESSON:** when a periodic "repair" job reads one store and writes another, it has a race with the live path by construction. Make the repair conditional (WATCH/version, or a conditional UPDATE) rather than hoping the window is small — same shape as the frontier's conditional claim.

- **2026-11-24 (final) — CDN exemptions, audit trail, auth cost.**
  1. **CDN exemptions** (`services/ipPolicy.ts`). Tried to fetch Cloudflare's and Fastly's published range lists to ship as defaults; the hosts don't resolve from this sandbox, so **no ranges ship** — hardcoding ranges from memory risks a wrong range silently unprotecting real servers. Instead: `CRAWLER_IP_EXEMPT_CIDRS` (static) + `CRAWLER_IP_EXEMPT_SOURCES` (published lists, text or JSON, CIDR tokens extracted + validated), refreshed by the maintenance loop into one Redis SET per source; a failed fetch keeps the last good list. Workers match with `net.BlockList` (no dependency), cached 60s. Exempt IPs skip only the IP lock. Admin panel shows sources, counts, errors, and a refresh button. Tested with local fixture lists (text, JSON, one that fails after its first fetch).
  2. **Audit trail** (`services/audit.ts`, `audit_log`): every sign-in (incl. failures, attempted username, IP, UA) and every state change, never secrets. Append-only via an UPDATE trigger; retention job is the only delete path (`AUDIT_RETENTION_DAYS`, 365). Keyset-paginated admin API + panel. **Found by the test:** the first schema had `actor_id REFERENCES users ON DELETE SET NULL`; deleting a user made Postgres UPDATE audit rows, the trigger refused, and user deletion returned 500. Dropped the FK (and `DROP CONSTRAINT IF EXISTS` on upgrade, verified against a DB that had it) — history must not depend on the users table; `actor_username` is denormalized.
  3. **Auth cost, not JWT.** Kept sessions (repo default; JWT would need a per-request denylist for the immediate revocation we rely on). Removed the per-request Postgres lookup: `crawler:auth:user:{id}` in Redis, written through after each account mutation commits via a Lua set-if-newer on `session_version` (monotonic), tombstone on delete. Test asserts 0 `users` queries over 10 protected requests (spy on `pool.query`), that a stale cache write after a revocation is rejected, and that a tombstone can't be resurrected. Added "sign out everywhere" (admin, per user) and "sign out other sessions" (self). Prometheus `crawler_auth_cache_lookups_total{result}`.
- **LESSON:** two safety mechanisms can fight each other — an immutability trigger and an `ON DELETE SET NULL` foreign key were each correct alone. Only an end-to-end test that exercised both (delete a user who has audit history) surfaced it.

## Notes / Known Gaps

- **Accounts:** bootstrap admin `admin` / `password123` (env `ADMIN_USERNAME` / `ADMIN_PASSWORD`, applied only when no active admin exists). More accounts via the Admin page or `/api/admin/users`. Change accounts through the service/API, not raw SQL: the auth cache only sees writes made through `services/users.ts` (a direct `UPDATE users` is invisible until the 10-minute TTL).
- **Audit writes are best-effort**: awaited, but a failed insert is logged, not turned into a failed request (the action already happened). Audit in the same transaction, or an external sink, if entries must never be lost.
- **No default CDN ranges**: configure `CRAWLER_IP_EXEMPT_SOURCES` with the providers' published lists.
- **Integration tests are destructive**: `npm run test:integration` flushes the Redis DB and truncates crawler tables. Stop any running API/workers first — they share the stores and will race the tests.
- **Screenshot harness** launches WebKit; not runnable in containers that only ship Chromium. The generated Playwright smoke tests (Chromium) cover the same login flow.
- **Per-IP lock vs worker idle poll:** workers sleep 500ms when nothing is claimable, so with the default 250ms IP delay the observed spacing on a single shared host is ~500ms, not 250ms. The lock is the guarantee; the poll interval is the practical floor.
