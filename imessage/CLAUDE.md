# iMessage — Development with Claude

## Project Context

The unit of identity in most systems is the user. In a messaging system it has to be the **device**, and almost every hard problem here follows from that. A message isn't delivered to Alice — it's delivered to Alice's phone, her laptop, and her tablet, each of which may be online, offline, or newly registered. Read state is per-device (reading on the phone should clear the badge on the laptop). Delivery receipts are per-device. In a real E2E design even the encryption key is per-device, because a device that didn't exist when a message was sent must not be able to read it.

That fan-out shape is what makes "did this message arrive?" a genuinely hard question. The sender's phone is online, the recipient has three devices, one of which is in airplane mode — the message has to be durably queued for that one, delivered instantly to the other two, and none of it can block the sender's UI. So delivery is split: the send transaction writes one `device_inbox` row per recipient device (including the sender's other devices), a Redis pub/sub bus pushes the message to whichever server instance holds each live socket, and a device's acknowledgement is the only thing that removes its row. A device that was away drains its inbox when it reconnects.

The second theme is that a phone on a flaky network retries, and a retried "send" must not produce two messages — and everyone must see the conversation in the same order. Every message gets a per-conversation `seq` under the conversation row lock, and the client-generated `clientMessageId` is unique per `(conversation, sender)` on the message row itself, so a retry returns the original message (and the seq it already has) instead of inserting again.

**Learning goals:** device-centric data modeling, per-conversation ordering with sequence numbers, per-device delivery with acknowledgements and catch-up, idempotent sends over an unreliable client, receipts as monotonic state, WebSocket delivery across multiple server instances via Redis pub/sub, and a schema that anticipates E2E encryption without the server ever holding plaintext.

`backend/src/services/messages.ts` holds the send transaction (seq + membership check + idempotent insert + inbox fan-out), inbox drain/ack and the read watermark. `services/websocket.ts` authenticates sockets, processes each socket's frames in order, pushes the inbox on connect, and forwards pub/sub events to local sockets; `services/realtime.ts` owns the channel contract. `shared/connection-registry.ts` tracks every socket per device; `shared/rate-limiter.ts` is shared by REST and WebSocket sends.

Frontend is React 19 + TanStack Router + Zustand + Tailwind: `ConversationList`, `ChatView`, `MessageBubble`, `ConnectionBanner`. `lib/messageList.ts` holds the merge rules (dedupe by ID, order by seq, statuses only move forward, gap detection); `stores/chatStore.ts` routes every incoming frame through them and acks; `services/websocket.ts` reconnects forever with jittered backoff and keeps an outbox. Vite proxies `/api` and `/ws` → `localhost:3000`.

## Key Design Decisions

### 1. Device is the primary entity; user is a grouping over devices
`devices` is a first-class table keyed per `(user_id, install_id)` — the browser keeps a random installation ID in `localStorage` — `sessions` carry a `device_id`, the inbox and both receipt tables are keyed on the device, and the connection registry tracks every socket of a device (two tabs are one device with two sockets).

Modeling per-user instead is simpler and produces immediately visible bugs. Read state is the clearest: with one read pointer per user, reading a conversation on your laptop marks it read everywhere — which is arguably what you want — but *delivery* per-user is incoherent, because "delivered" would be true the moment any one device received it, and the phone in your pocket that never got it would never be retried. Per-device delivery means the offline queue has an exact addressee. The other reason is forward-looking: in a real E2E design each device holds its own keypair, so a message key must be wrapped once per recipient device (`message_keys` is keyed `(message_id, device_id)` for exactly this). A user-level model has nowhere to put that.

What we give up is fan-out cost that scales with total device count, not user count. A 10-person group where everyone has 3 devices means 30 encrypted key blobs per message and 30 delivery rows. That's the real reason group messaging at scale moves to sender-keys — one key per conversation, distributed pairwise once — rather than the per-device wrapping this schema does.

### 2. Live routing is Redis pub/sub broadcast, not sticky sessions
After the send commits, the server publishes to a Redis channel; every instance receives it and delivers to whichever of the target devices it happens to hold.

Sticky sessions — pinning a user to one instance at the load balancer — would let a server deliver locally with no broker. It breaks on the fundamental asymmetry of chat: the *sender* and the *recipient* are different users, so even perfect stickiness puts them on different instances most of the time. Stickiness only helps if you pin by *conversation*, which fails as soon as a user is in many conversations and would need many affinities at once. Pub/sub sidesteps the question entirely: any instance can accept any connection, and delivery is a broadcast that all but one instance ignores.

The cost is that every message is delivered to every instance regardless of relevance — at N instances that's N× the fan-out traffic for one recipient's benefit. Fine at 3 instances, wasteful at 300, which is where a `device → server` registry would earn its keep. The old code maintained one in a Redis hash that nothing read for routing (and that a closing tab could wipe while another tab of the same device was still open); it was removed in the 2026-10-10 pass, and presence now uses a per-connection sorted set instead.

### 3. Delivery state is a per-device inbox in PostgreSQL, written in the send transaction
`sendMessage` inserts one `device_inbox` row for every active device of every participant except the sending device, in the same transaction as the message. The socket handler pushes the oldest 200 rows on connect (`sync_batch`); the client acks what it applied, and `acknowledgeDelivery` deletes those rows and writes `delivery_receipts` in one statement. An hourly sweep drops rows older than `INBOX_RETENTION_DAYS` (30).

This replaced a Redis list per device (`RPUSH` on send, `LRANGE` then `DEL` on connect) that was wrong in three ways: the batch was deleted before the client had processed it, so a drop mid-drain lost it; every instance enqueued its own copy of each pub/sub event; and it only queued when the user had no connection *anywhere*, so a user with their phone online never got messages queued for their laptop. Reconstructing "what did I miss" from cursors per conversation was the other alternative, and it turns every reconnect into a query across all of a user's conversations. The cost of the inbox is write amplification (one row per recipient device per message) and the fact that a device that never comes back holds rows until the sweep — which the seeded phone/tablet devices do.

### 4. Ordering and idempotency live on the message row
`conversations.last_seq + 1` is taken with an `UPDATE … RETURNING` whose `WHERE` also checks membership; the row lock serializes senders until COMMIT, so seq order equals commit order. The insert uses `ON CONFLICT (conversation_id, sender_id, client_message_id) DO NOTHING`; zero rows means a retry, so the transaction rolls back (returning the seq) and the original message is returned — or `422`/`idempotency_conflict` if the same ID carries different content.

The server cannot deduplicate on its own — sending "ok" twice on purpose is normal — so the client generates the ID at compose time and reuses it across retries. The old implementation checked Redis and an `idempotency_keys` table *before* inserting (two concurrent retries could both pass) and, worse, the WebSocket handler never passed `clientMessageId` to it, so the path every message actually took had no protection. Ordering was `created_at`, which ties and can commit out of order. What we give up: correctness still depends on client discipline, and the constraint never expires (fine with UUIDs).

### 5. The schema is E2E-ready; the implementation is not, and that's explicit
`messages` has both `content` (plaintext) and `encrypted_content` + `iv`; `device_keys` holds identity and signing public keys; `prekeys` models X3DH one-time keys with a `used` flag. **No client-side cryptography exists** — messages are sent and stored as plaintext in `content`.

This is a deliberate split rather than an oversight. The interesting *systems* problems — per-device fan-out, key distribution shape, prekey exhaustion, the fact that the server must be able to route and queue data it cannot read — are all visible in the schema and the delivery paths. Implementing X3DH and Double Ratchet correctly in the browser is a large, self-contained cryptography project that would teach key management rather than distributed messaging, and getting it subtly wrong produces something that *looks* encrypted while being insecure. Half-built encryption is worse than none, because it invites trust it hasn't earned. The columns document the intended design; the plaintext path makes it clear nothing is actually protected.

## Current State

Runs end to end. `docker-compose up -d` starts Postgres (schema auto-loaded from `backend/src/db/init.sql`, which is re-runnable and backfills `seq` on older databases) and Valkey; `npm run dev` starts the API and WebSocket server on 3000. Working: registration and login with bcrypt, one device per (user, browser installation); direct (race-safe) and group conversations; sends over WebSocket or REST with per-conversation `seq`, membership checked in the send transaction, and idempotency on `clientMessageId`/`Idempotency-Key`; per-device inbox with acks, catch-up on connect and gap-triggered sync; delivery receipts and monotonic read watermarks that also sync to the reader's other devices; Sent → Delivered → Read in the UI (surviving reloads); reactions (participants only), typing with client-side expiry, presence that goes offline only when a user's last connection closes and is sent only to conversation peers; device revocation that kills Redis sessions and open sockets; an atomic Redis rate limit shared by REST and WebSocket sends; seq-based history pagination; metrics, structured logs, health checks and graceful shutdown. `npm test` runs 20 backend and 10 frontend unit tests.

Seeded logins, all with password `password123`: `alice@example.com`, `bob@example.com`, `charlie@example.com`, and `admin@example.com` (`system_admin` role). The seed includes direct and group conversations with message history and one pending inbox row for Alice's (never-connecting) MacBook.

Simplified or omitted: **no encryption** (decision 5); a single PostgreSQL plays both conversation and mailbox shards, so there is no outbox/Kafka/fan-out worker; pub/sub broadcast instead of targeted routing; no attachment upload, no push notifications, no message search; edits and deletes are not pushed to other devices; membership changes are not sequenced; the client keeps messages and its outbox in memory only (no IndexedDB, no list virtualization).

## Iteration & Repair Log

- **2026-07 (docs rewrite):** replaced the template phase-checklist CLAUDE.md with this structure. The old checklist was wrong in both directions: **"Phase 3: Multi-Device"** listed device registration, per-device encryption, message sync, and read-state sync as four unchecked boxes, when device registration happens on every login in `services/auth.ts`, connections are keyed by device, and `read_receipts` is primary-keyed `(user_id, device_id, conversation_id)` — device-centricity is the *foundation* of the implementation, not future work. Meanwhile Phase 2 was marked "In Progress" with all its boxes checked. The old file was 30 lines long and explained nothing about how delivery actually works.
- **Illegal partial-index predicate (fixed):** the sessions cleanup index was declared with a `WHERE expires_at < NOW()` predicate. Index predicates must be `IMMUTABLE`, and `NOW()` is `STABLE`, so Postgres rejected the statement — which aborted the whole `init.sql` load from `docker-entrypoint-initdb.d`, leaving a database with **no tables at all**. Because the container still accepted connections, this surfaced downstream as seeding "succeeding" against an empty schema and then every login failing. Now a plain `CREATE INDEX idx_sessions_expired ON sessions(expires_at)`; the time comparison belongs in the cleanup query, not the index. The genuinely-immutable partial indexes (`WHERE NOT used` on prekeys, `WHERE left_at IS NULL` on participants, `WHERE deleted_at IS NOT NULL` on messages) were kept.
- **Idempotency added to send:** retried sends over flaky mobile connections were duplicating messages into conversations (decision 4).
- **Conversation and participant caching:** every send did a participant-membership check against Postgres. `shared/conversation-cache.ts` now serves it from Redis with a 10-minute TTL and explicit invalidation on membership change, taking the database off the per-message hot path.
- **Broadcast excludes the sending device**, so the composing device isn't told about its own message and doesn't clobber the optimistic bubble it already rendered.
- **Heartbeat added:** sockets are ping-ponged with an `isAlive` flag, because a WebSocket to a device that dropped off the network stays "open" indefinitely on the server side, silently accumulating dead connections and making presence permanently wrong.
- **2026-10-10 (delivery semantics + docs rewrite):** verified the open questions against the code and rebuilt the delivery path around them. (1) *Ordering and idempotent send:* messages get a per-conversation `seq` taken under the conversation row lock (membership checked in the same `UPDATE`), and `client_message_id` is unique on the message row; the WebSocket send path had never passed `clientMessageId` to the old Redis+table idempotency check, which was itself check-then-act. `shared/idempotency.ts`, the `idempotency_keys` table and the never-imported `shared/conversation-cache.ts` were deleted. (2) *Per-device inbox:* the Redis offline lists (lossy `LRANGE`+`DEL`, one copy per instance, skipped devices of partly-online users) were replaced by `device_inbox` rows written in the send transaction, drained on connect and removed by acks that produce `delivery_receipt` events; `sync_cursors` was dropped. Socket frames are now processed in order per socket, with the handler attached before authentication finishes (frames flushed on open used to be dropped). (3) *Receipts:* read state is a monotonic `last_read_seq`, validated against the conversation and broadcast to the reader's own devices; unread counts use it instead of read timestamps. (4) *Device identity:* login matched devices by user-agent name, merging two identical browsers into one device; devices are now `(user_id, install_id)` upserts, and revocation finally deletes Redis sessions and closes sockets. (5) *Smaller fixes:* REST reactions lacked a participant check (any user could react to any message), read receipts accepted message IDs from other conversations, the WebSocket path bypassed the 60/min send limit (now one atomic Lua limiter for both paths, `RateLimit-*` headers, no per-user metric label), presence went offline when *any* device closed and was broadcast to every connected user, direct-conversation creation raced, the lazy Redis subscriber logged a spurious connection error at startup, and SIGTERM did not close sockets. On the client: the WebSocket service cleared all subscribers on logout (so logging back in left the tab with no real-time updates) and gave up after five reconnects; optimistic bubbles rendered as someone else's message; messages were sorted by mixed client/server clocks. Verified with `tsc`, lint, 30 unit tests, schema loaded twice plus an upgrade from the old schema with data, and a 38-check WebSocket end-to-end script against PostgreSQL + Redis. Rewrote `architecture.md` and the three interview answers around the production design (per-conversation seq, per-device mailbox, outbox → Kafka fan-out) with generated sequence diagrams.
- **CI:** the repo-wide smoke-test workflow was removed (a CI runner can't provide the Postgres/Redis services these tests need). Verification is local: `npm run type-check`, then `npm run triage imessage`.

## Open Questions

1. Pub/sub broadcasts every event to every instance. At what instance count is a `device → server` registry worth it, given that targeting adds a Redis lookup per recipient device and the entry goes stale the instant a device reconnects elsewhere? (The inbox makes a stale entry harmless — it only delays delivery.)
2. Edits, deletes and membership changes are not sequenced. Should they become `seq`-numbered events in the same stream (and inbox), so every device converges on them the way it converges on messages — and so "was Bob a member at seq 812?" has one answer?
3. Per-device message keys mean a 10-person group with 3 devices each needs 30 wrapped keys per message. Sender keys collapse that to one, at the cost of a re-key on every membership change. Where's the crossover, and does it change if most groups are small?
4. The web client keeps its outbox in memory, so a reload loses messages typed offline. Is IndexedDB persistence (plus single-socket tab leadership via `BroadcastChannel`) worth the complexity for a demo client?
5. Seeded phone/tablet devices never connect, so their inbox rows sit until the 30-day sweep. Should inactive devices stop receiving inbox rows after some idle period, the way real systems prune devices that have not checked in?
