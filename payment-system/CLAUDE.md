# Payment System — Development with Claude

## Project Context

A merchant payment platform: merchants authenticate with an API key and drive payments through the full lifecycle — authorize, capture, void, refund, chargeback — while every balance change is recorded in a **double-entry ledger**. The core hard problem is *money correctness under retries*: a network timeout must never double-charge a customer, and the sum of debits must always equal the sum of credits. That forces two disciplines everywhere — idempotency on every mutation, and paired ledger entries inside a single database transaction.

**Learning goals:** double-entry bookkeeping as a correctness invariant, idempotency-key design, circuit-breaker isolation of an unreliable external processor, and async fan-out (webhooks, fraud scoring) without blocking the payment path.

## Architecture at a Glance (what actually runs)

Three infrastructure services in `docker-compose.yml`, each on the hot path for a different reason:

| Store | Role | Why this one |
|-------|------|--------------|
| **PostgreSQL** (`pg`) | Transactions (each row is also its idempotency record), `ledger_entries` grouped into journals, merchants, refunds, chargebacks, webhook deliveries, audit log | ACID — a payment's claim, status change, journal and refund limit must commit together; triggers enforce journal balance and an append-only ledger |
| **Valkey/Redis** (`ioredis`) | The simulated processor's own records (`psp-sim:*`), health checks | Deliberately *not* on the idempotency path since 2026-10: a cache cannot be the durable record of whether a customer was charged |
| **RabbitMQ** (`amqplib`) | `webhook.delivery` + `fraud.scoring` queues consumed by background workers | Decouples slow/failure-prone side effects (merchant webhook endpoints, deep fraud analysis) from the synchronous payment response |

Backend is a single Express app (`backend/src/index.ts`) plus three standalone workers: `workers/reconciler.ts` (PostgreSQL + Redis only) and the RabbitMQ consumers `workers/webhook-worker.ts` and `workers/fraud-worker.ts`. Routes: `payments`, `refunds`, `chargebacks`, `merchants`, `ledger`. Services: `payment/` (authorize/capture/void/processor/reconcile, plus `state-machine.ts` and `errors.ts`), `ledger.service`, `merchant.service`, `fraud.service`, `refund.service`. Frontend: React 19 + TanStack Router + Zustand (merchant dashboard).

## Key Design Decisions

### 1. Double-entry ledger as the source of truth, enforced by the database
Money moves in journals: entries posted together (`ledger_entries.journal_id`) whose debits equal their credits. A capture is three entries (debit Accounts Receivable gross, credit the merchant net, credit Platform Revenue fee); refunds mirror the refunded share with cumulative fee rounding; chargebacks add a 15.00 fee. Pure builders in `ledger.service.ts` produce the lines, `postJournal()` refuses an unbalanced set, and `init.sql` adds a `DEFERRABLE INITIALLY DEFERRED` constraint trigger that re-checks every journal at COMMIT plus a trigger that makes `ledger_entries` append-only. Balances are credit-positive (receivables reads negative; all balances sum to zero), updated with `balance = balance + delta` under the row lock in account-id order. Trade-off given up: three entries and three balance updates per capture instead of one `UPDATE`, and hot platform-account rows at scale.

### 2. Idempotency on the payment row, not in a cache
`POST /payments` inserts the payment as `pending` with `ON CONFLICT (merchant_id, idempotency_key) DO NOTHING`; the request that gets the row back owns the key and calls the processor, everyone else reads the row and compares a SHA-256 request fingerprint (`200` replay of the current state, `409` while pending, `422` for a different body). Refunds do the same under the payment's row lock. The payment id is the processor's idempotency reference, so no retry — ours or the reconciler's — can authorize twice. Trade-off: a unique index that grows with the table forever (fine locally; it is why the production design shards by merchant rather than partitioning by time).

### 3. Circuit breaker around the external processor
Processor calls (`services/payment/processor.ts`) run through a **cockatiel** circuit breaker (`shared/circuit-breaker.ts`), not raw calls. After a failure threshold the breaker opens and fails fast instead of letting requests pile up against a dead processor and exhaust connection pools. Every call is classified as `approved`, `declined`, `not_attempted` (breaker open: safe to fail) or `unknown` (timeout after sending: the card may be charged). Unknown payments stay `pending`, the API answers `202`, and the reconciler asks the processor about the reference. The processor is *simulated* with its own records in Redis (test cards `0000` decline, `0001` lost response, `0002` lost request; `PSP_DECLINE_RATE` random declines). Trade-off: fail-fast means some payments are rejected during a processor blip that a longer timeout might have ridden out — acceptable because a responsive "try again" beats a hung request pool.

### 4. bcrypt API keys, linear scan (local simplification)
Merchant keys are generated as `pk_<uuid>` and stored as **bcrypt** hashes (`merchant.service.ts`). Because bcrypt hashes aren't reversible or indexable, `authenticateByApiKey` loads active merchants and `bcrypt.compare`s against each — fine for a handful of local merchants, explicitly flagged in-code as needing a key-id lookup at scale. This is the auth model to remember: **API-key merchant auth, not username/password sessions.**

### 5. Async side effects over inline processing
After a payment commits, webhook delivery and deep fraud scoring are published to RabbitMQ and handled by workers with retry/backoff, rather than run inline. Trade-off: the merchant's webhook and the final fraud verdict are eventually-consistent with the payment, but the customer-facing authorize/capture response isn't held hostage to a slow merchant endpoint.

## Current State

Implemented end to end: API-key auth, payment authorize/capture/void through a guarded state machine (`state-machine.ts`, compare-and-set `UPDATE ... WHERE status = ANY(...)`), full and partial refunds under a `SELECT ... FOR UPDATE` row lock, chargeback journals (service only; no route creates one), journals whose balance PostgreSQL enforces at commit, per-merchant idempotency stored on the payment and refund rows, a simulated processor with reference-level idempotency, a reconciler worker for unknown outcomes, ledger verification (window totals, unbalanced journals, account drift), RabbitMQ webhook and fraud workers, Prometheus metrics, Pino logging with an `audit_log` table, and a merchant dashboard that sends one idempotency key per payment or refund draft.

**Tests:** `cd backend && npm test` runs 22 offline vitest tests (journal builders and fee rounding, `postJournal`, state-machine SQL, request fingerprints, reconciler decisions).

Seeded from `backend/db-seed/seed.sql`: merchant **Acme Payments**, API key **`pk_test_5a8f3c2e1b9d4f6a7c0e2d1b`** (paste it on the login page — auth is an API key, not a username/password), with nine transactions spanning every lifecycle state, nine balanced journals (six captures, a full and a partial refund, a chargeback), account balances equal to the sum of their entries, and webhook deliveries.

Intentionally omitted / simulated: real processor integration, a transactional outbox (webhooks are published best effort after commit), hold-expiry tracking, settlement-file reconciliation, payouts, multi-currency conversion, rate limiting, and admin session auth (the dashboard uses the merchant API key).

## Open Questions

1. `authenticateByApiKey` bcrypt-compares against every active merchant per request. Random API keys are high-entropy, so SHA-256 behind an indexed `key_id` (`pk_<key_id>_<secret>`) would be both faster and sufficient — when is it worth migrating the seeded key format?
2. Webhooks are still published to RabbitMQ after commit (a dual write: a crash in between loses the event). Is a transactional outbox worth adding locally, given the relay would need RabbitMQ to verify?
3. The dashboard stores the merchant's secret API key in `localStorage`; any XSS would expose a full-access key. Should the dashboard get session auth now, or is that out of scope for this project?
4. The reconciler gives up after 10 attempts and only logs. What should "needs manual review" look like — a status, an admin view, an alert?
5. Chargebacks are recorded but there is no route to create one and no evidence/dispute lifecycle. Where should that state machine live?
